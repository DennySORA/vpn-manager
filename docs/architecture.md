# VPN Manager 架構設計

這份文件說明 VPN Manager 的設計與取捨，以及每個元件在程式碼裡的位置。它是設計的依據：實作和這裡不一致時，以程式碼的現況為準，並把這份文件改正。一開始的構想裡後來改掉或拿掉的部分，連同理由列在 §9。

## 1. 產品是什麼

本機的 WireGuard 多出口管理器。使用者建立多個彼此獨立的 VPN **Instance**（各自一條 WireGuard tunnel），把指定的 **Gateway**（loopback 上的 SOCKS5／HTTP 代理）、受管 **App** 與 **Port forward** 綁到某個 Instance。主機的 default route、系統 DNS、其他 App 完全不變——沒有「全機 VPN」模式。

核心承諾只有一句：**受保護的流量只有兩種結局——經它所屬 Instance 的 tunnel 送出，或失敗。** 任何故障（斷線、崩潰、重啟、睡眠、設定錯誤）都不能把它變成直連。

非目標：登入／帳號／RBAC、手機版、全機 VPN、匿名性承諾、對抗已取得同 UID 或 root 的本機攻擊者。管理介面預設只在 loopback；開放給區網是安裝時的明確選擇（只限列出的網段、沒有登入；§8 第 10 條、§9）。

單一執行檔 `vpnd` 以角色啟動：`vpnd controller`、`vpnd manager`、`vpnd instance`（只由 manager 以 re-exec 自身產生，不接受使用者啟動）。另有 CLI `vpnctl` 與測試用的受控 WireGuard 對端 `vpn-labpeer`。瀏覽器預設只經 `127.0.0.1` 連到 controller；以 `--listen-address`＋`--allow-client` 安裝時，列出網段裡的其他主機也能連（§5.5、§8 第 10 條）。

為什麼這樣切（取捨見 §9）：

- **Controller 無狀態**：UI/API/Provider 程式碼變動最頻繁，重啟或崩潰不影響任何 tunnel，也不持有任何持久真相。
- **Manager 是唯一長駐核心**：Instance 生命週期、持久意圖（Store）、秘密交付、OS 操作放在同一個小而穩定的程序；它不載入 Web、Provider、TLS 客戶端等大型攻擊面。重開機恢復只依賴這一個程序與本機磁碟／keystore。
- **每個 Instance 一個 worker 程序**：崩潰、記憶體、FD、GotaTun 狀態完全隔離；換 generation＝換程序，舊程序死亡即代表舊 FD／金鑰租約結束，不需要「收養存活 worker」的協議。
- **worker 只用兩條工作執行緒**（2026-11-11，`crates/vpnd/src/main.rs` 的 `instance_worker_threads`）：三個角色原本都是每個核心一條執行緒（32 核心的主機上每個程序 33–39 條）。連線的 worker 把每個封包交給一串工作（代理埠、netstack 或沙箱 socket、tunnel），執行緒一多，交接幾乎每次都要叫醒另一條執行緒。量測（32 核心的 PC，release 建置的開發堆疊；1、4、12 個下載同時經 SOCKS5 代理埠從 lab 對端抓資料，每種各 5 輪、每輪 8 秒，取中位數）：32 條時 80–122 MiB/s、每 GiB 用 6.3–8.4 秒 CPU、約 41–57 萬次 context switch；2 條時 179–217 MiB/s、3.2–3.9 秒、約 14–15 萬次。嚴格隔離：66–107 MiB/s、9.7–13.5 秒，對 129–214 MiB/s、4.2–4.4 秒。1 條的 CPU 最省（2.2–2.9 秒，context switch 降到約 1 千次以下）、12 個下載時也最快（252–258 MiB/s），但嚴格隔離的單一下載比 2 條慢（93 對 129 MiB/s），而且一個工作佔住執行緒時其他全部停住，所以取 2 條（單核心主機 1 條）。manager 與 controller 維持每個核心一條：manager 降到 4、2、1 條時經 SSH 拉檔案沒有比較快（64–84 MiB/s，各 3 輪，彼此在誤差內）、CPU 相同（每 GiB 2.5–2.7 秒）；controller 降到 4 條以下時每秒能回答的請求少四分之一（648 → 約 485，p95 15 → 20 毫秒）。這些數字來自同一台主機上的 loopback 路徑，不是實際的 VPN 線路；小型主機（核心數 ≤ 2）的行為不變。
- **鎖來自 `crates/sync`（`vpn-sync`），什麼時候把鎖交給等待者由這個專案自己決定**（2026-11-11）：workspace 的 `Mutex` 與 `RwLock` 是 `vpn-sync` 包住的 parking_lot 0.13。parking_lot 解鎖時不排隊——誰先要就給誰，剛解鎖的執行緒可以在等待者醒來之前再拿一次，這是它快的原因。0.12 以前它自己每隔隨機的 0–1 毫秒把有人等的鎖直接交給等待者一次；0.13 拿掉了，只留明確的公平解鎖。少了這一層，在迴圈裡反覆取鎖的執行緒（忙碌時的 netstack pump）可以一直把別人擋在外面。規則（`handover.rs`）：等鎖的執行緒自己計時，等了 250 微秒還沒拿到就算**被餓到**；只要有執行緒被餓到，每一次解鎖都把鎖直接交給排最久的那一個，鎖變成先到先得，直到每個人又都能在 250 微秒內拿到為止；其餘時候照舊不排隊。解鎖的一方只多讀一個計數；沒有人競爭時一次上鎖加解鎖 8.5 奈秒，與 parking_lot 相同。其他 crate 不能自己相依這一代的 parking_lot（`deny.toml` 的 `bans.deny`，違反時 cargo-deny 失敗）。tokio 與 GotaTun 內部仍用 0.12（它們自己的鎖，行為沒有變），所以同一個程序裡有兩代，`vpnd` 比升級前大 424 KiB（0.8%）。量測（32 核心的 PC，獨立的探針程式，每種情境 2 秒、至少 2 輪；機器上同時有別的工作）：
  - 一條執行緒不間斷地取鎖（每次持有 20、100 或 300 微秒），另一條每 200 微秒要一次。純 0.13：後者整段都拿不到（沒有設時限的那一次等了 57 秒）。0.12：中位數 0.25–0.40 毫秒、最久 0.8–1.0 毫秒。現在：中位數 0.27–0.40 毫秒、最久 0.29–0.47 毫秒（十幾次裡有一次 0.89）。
  - 多條執行緒搶同一把鎖（鎖內 2 微秒、鎖外 1 微秒），吞吐與 0.13 比、最久等待與 0.12／0.13 比。4 條：少 1–2%，0.3–0.9 毫秒（原本 7–88 毫秒）。16 條：少 4–5%，0.4–0.8 毫秒（25–70 毫秒）。32 條：少約 11%，0.5–0.9 毫秒（47–113 毫秒）。64 與 128 條（比核心多）：少約 20%，0.6–3.2 毫秒（90–190 毫秒）。鎖內 50 微秒時吞吐完全相同，最久等待是原本的三分之一以下。兩條執行緒只搶鎖、鎖內外都不做事時，吞吐比 0.13 少一成上下（等待的一方多讀一次時鐘）。
  - 取捨：試過「每 250 微秒最多交 2、4、8 次」的上限——32 條時吞吐只少 2–4%，但最久等待回到 4–16 毫秒；也試過讓解鎖的一方計時——極短臨界區的吞吐少四成。產品裡沒有被十幾條執行緒塞滿的鎖（連線的 worker 只有兩條執行緒），所以取保證最強、也最簡單的做法。上鎖的快路徑維持 parking_lot 的單一 compare-and-swap：改成先 `try_lock` 再走冷路徑可以讓執行檔小 66 KiB，但每次上鎖多 2.7 奈秒（8.5 → 11.2）。
  - 開發堆疊（升級前的 build、現在、不交鎖的 0.13，以及 100 與 500 微秒兩個對照；同一個 lab 對端的執行檔，輪流量）分不出差別：1、4、12 個下載的吞吐單次在 45–500 MiB/s 之間，各版本 10 輪的中位數互有高低；下載佔滿連線時每毫秒送一個小請求，中位數 0.11–0.37 毫秒、p99 0.54–1.55 毫秒，worker 每 GiB 用 2.9–3.6 秒 CPU、15.6–17.4 萬次 context switch，五個版本都在同一個範圍。探針裡的飢餓在這條路徑上沒有出現；這個機制保的是最壞情況。

## 4. 資料面

### 4.1 共通：Instance worker 內的路徑

`Gateway/DNS/Port forward → TunnelConnector → Netstack → IpChannel → GotaTun Device → PinnedUdp → peer`

- **GotaTun** 以 crate 直接嵌入（`=0.10.3`），使用 `DeviceBuilder::with_ip_pair` 接自己的有界 IP channel，`with_udp` 接自己的 `PinnedUdpFactory`。不 fork、不 vendor、不執行任何外部 wg／wireguard-go。
- **PinnedUdpFactory**：underlay socket 只送往 profile 宣告的 peer endpoint（數字 IP:port），也只接受來自該位址的封包；GotaTun 的 endpoint roaming 不能把加密流量導向任意位址。
- **Netstack**：每 Instance 一個 smoltcp `Interface`（Medium::Ip，tunnel 位址來自 profile），單一 owner task 以 waker／deadline 驅動，不 busy-loop。smoltcp 是 0.14.0 加上三個修補（`vendor/smoltcp`，以 `[patch.crates-io]` 取代 crates.io 版本；內容、證據與何時移除見 `vendor/README.md`）：兩個 TCP 修正——逾時重送後的 ACK／RST 帶最高已送序號，以及只剩 FIN 在途時快速重傳仍會送出，兩者都曾讓 TCP 流卡住——以及讓緩衝能在連線中放大（§4.5）。對外只暴露 `TunnelConnector`：`connect_tcp`、`bind_udp`、`listen_tcp`、`listen_udp`。**worker 裡沒有任何會連到任意目的地的 host socket**——結構上不存在直連路徑，而不是靠檢查擋住。
- **Payload gate**：worker 有一個由 manager 控制的閘門（`closed → probe → open`、`sealed` 為終態）。收緊時**新**連線被拒（SOCKS5 回 `0x02` connection not allowed by ruleset、HTTP 回 503 與原因，原因的語言依請求的 `Accept-Language`，沒有可用的語言時英文，§7d）；tunnel 握手與 DNS 健康探測不受影響。代理埠本身停止或換代時（連線重建資料面），HTTP 代理對還沒回答的請求回 503 與原因，最多等 250 毫秒讓用戶端收走，不再讀新的請求；CONNECT 的轉送與 SOCKS5 連線立刻結束（2026-11-11：之前還在解析名稱或連線中的 HTTP 請求會被直接切斷，用戶端只看到連線關閉）。剛連上、請求還沒被讀到的連線也一樣：先等它的請求標頭（同樣最多 250 毫秒，混合埠連協定偵測在內），回 503 並關閉，而不是不讀就關（用戶端會收到重設）。WireGuard 裝置回報無法繼續的錯誤時（例如對端的 port 拒絕），worker 先這樣結束自己的代理埠、再回報給 manager：manager 一收到就結束這個 worker，之前處理中的請求因此沒有任何回答（2026-11-11，洩漏矩陣 `d_dns_down_strict` 第三輪；`controller.rs` 的 `end_gateways`）。
- **暫時故障不拆既有連線**：既有 flow 本來就只能進 GotaTun，tunnel 斷線時它們只是停住、由 TCP 自行重傳，沒有任何直連可能；所以 peer 暫時無回應、睡眠喚醒、網路抖動只停止接新連線（gate→probe），既有 SSH 等長連線恢復後可繼續。只有換代、Stop、急停、seal 才主動 reset 既有 flow。
- **有界**：每 flow 的 TCP buffer、每 Gateway／Instance 的連線數、UDP association、DNS in-flight、IP channel 都有上限；滿了就拒絕或丟棄，不排無界佇列。使用者態 TCP/IP 的連線數上限在檢查的同一步取得名額（`crates/tunnel/src/netstack/mod.rs` 的 `reserve`）：連出的 TCP 與 UDP socket 從這裡佔一格到 flow 移除為止，並行的呼叫不會一起擠過最後一格；監聽中的 socket 不佔格（上限已滿時不再新增），它接受的連線在接受時才計入，所以連入的連線最多可以超過上限「已在監聽的 socket 數」。
- **DNS（Instance DNS Controller，`crates/instance/src/dns`）**：查詢一律經 tunnel 送到連線的 DNS 伺服器（DNS 設定的，沒有指定時是 WireGuard 設定宣告的，以 UDP 送出）。一次查詢在一個期限內依序嘗試：下一個伺服器在前一個失敗時、或分到的時間（剩下的時間÷剩下的嘗試，至少 100 ms）到了時開始，最多同時 4 個（每個伺服器一個）；先到的有效回答勝出。**加密的嘗試不中斷（2026-11-07）**：同時的嘗試都在進行時，只有 UDP 的嘗試讓位（它的 datagram 多半丟了），TCP、DoT、DoH 的嘗試一直等到回答、失敗或期限——之前最多同時 2 個、最舊的讓位，DoT／DoH 的嘗試只活大約兩個分到的時間（4 秒、4 個伺服器 × 2 輪時約 1 秒），經遠的出口（跨洲）冷啟動的 TCP＋TLS＋HTTP/2 交握要好幾個往返，於是沒有一個完成，NextDNS 的 DNS 設定在一條遠方出口的嚴格隔離連線上一直探測失敗、資料面每 30 秒重建。以延遲轉送（單向 220 ms）重現：每個伺服器單獨都通過，四個一起在 4.000 秒失敗；修正後四個一起 1.5–2.1 秒通過。**DNS 設定全部失敗時改用 WireGuard 設定的 DNS**：有 DNS 設定的連線把 WireGuard 設定宣告的 DNS 當作備援（`DnsSpec.fallback`，最多 4 個、UDP、同樣經 tunnel；使用者自己的 IP 封鎖清單涵蓋的不用——DNS 自己的連線不經清單，使用者的規則優先）；健康探測發現 DNS 設定的每個伺服器都失敗時改問備援，備援回答就把查詢交給它，直到之後的探測發現 DNS 設定的伺服器回答了才改回，改回時清掉快取（備援的回答不經 DNS 設定的過濾，不留到之後）。連線的狀態 `DnsStatus.fallback` 寫出 DNS 設定的伺服器各自為什麼失敗；探測失敗時 `last_error` 同樣逐一寫出（`DoH 45.90.28.0:443 4.0 秒內沒有回應；DoT … 連線被拒`，只有伺服器、協定與原因，沒有查詢的名稱）；manager 在原因改變時以 warn 記一次，恢復時以 info 記一次。網頁在連線的每個分頁開頭顯示備援說明與原因，連線列入「需要處理」。DNS 設定與 WireGuard 設定都沒有可用的伺服器時，照舊不就緒（不會改用系統 DNS）。**DNS 設定可以選擇失敗時中斷（2026-11-08；例如 NextDNS 連不到時就中斷）**：`DnsProfile.on_failure` 是 `wireguard_resolvers`（上面的備援；預設，之前存的設定沒有這個欄位時也是）或 `fail`。`fail` 時 manager 不把 WireGuard 設定的 DNS 交給 worker（`DnsSpec.fallback` 是空的；worker 收到了也不用）；健康探測發現每個伺服器都失敗時 DNS 進入中斷：之後需要上游回答的查詢立刻失敗、什麼都不送出（App 收到 SERVFAIL，代理埠回一般失敗或 502「DNS 已中斷」），快取裡 DNS 設定自己的回答照常到期為止；中斷時探測每 5 秒再試一次，伺服器回答就恢復。中斷時沒有名稱能證明 tunnel 活著，所以 worker 改看 WireGuard 工作階段：最後一次握手在 180 秒內（GotaTun 的 `REJECT_AFTER_TIME`；探測持續經 tunnel 送出，活著的對端在送出後 15 秒沒有回應就會重新握手、送資料時每 120 秒換一次金鑰）就不算 tunnel 故障，連線照常就緒、gate 保持開啟（`Probe` 的 `ok` 加上 `interrupted`），直接用 IP 的連線不受影響；超過 180 秒才和探測失敗一樣計入 watchdog。狀態 `DnsStatus.interrupted` 寫出各伺服器的原因、`healthy` 為 false；manager 在原因改變時以 warn 記一次；網頁在連線的每個分頁開頭顯示（danger），連線列入「需要處理」，`vpnctl instance inspect` 的 DNS 行也寫出。改這個選擇和改其他 DNS 設定一樣要重新啟動連線才套用（`pending_changes` 的 `dns`）。代價：中斷期間 tunnel 若真的斷了，要等工作階段超過 180 秒才發現（平常兩次探測失敗，約 60 秒）；這條連線若是 Provider 出口，供應商的 API 在中斷期間也解析不到名稱。
- **目的地政策（安全設定）**：每個新的出站連線依序檢查：系統規則（loopback、link-local、multicast、主機本身與其他連線永遠拒絕）→ 連線沒有的 IP 版本 → 私網需要允許 → 允許的目的地 → 允許的 port → 封鎖的 port → IP 封鎖清單與自動封鎖；前面拒絕的，後面的規則打不開（`crates/instance/src/policy.rs`）。基本規則隨 generation 固定，改了要重新啟動（`pending_changes` 標 `security`）。IP 封鎖清單是 overlay：manager 把使用中的清單合併成一個 `IpRangeSet`（排序、不重疊的範圍，二分搜尋；標準編碼的 SHA-256 為 digest），配上全域單調的 `enforcement_policy_revision`，以 `SetOverlay` 送給執行中的 worker 原子替換；worker 回報自己算的 digest，manager 把已套用的版本寫進狀態，不符就讓該 generation 失敗。換上新 overlay 時，連到新封鎖位址的既有 TCP flow 會被 reset。清單不能包含連線需要的 WireGuard 對端或 DNS 伺服器：儲存時拒絕並指出位址。
- **預設政策與內建 IP 封鎖清單（2026-11-02）**：沒有選安全設定的連線套用預設政策＝所有啟用中的內建清單＋自動封鎖；選了安全設定的連線完全依該設定的選擇。內建清單是程式的一部分（`crates/domain/src/builtin_blocklists.rs`）：Spamhaus DROP（IPv4、IPv6，JSON lines，每 24 小時）與 DShield 建議封鎖清單（SANS ISC，每 6 小時）；2026-11-07 起另有 FireHOL Level 1（GitHub 副本，每 24 小時）、abuse.ch Feodo Tracker 建議清單（每 12 小時）、Emerging Threats 已入侵主機（每 24 小時）、CINS Army（每 24 小時）、blocklist.de 全部（IPv4＋IPv6，每 12 小時）與 IPsum Level 3（每 24 小時），都是每行一個位址或 CIDR。程式加入新的目錄項目時，下一次啟動就建立它（使用者刪除過的不會再建立）；使用者已有同一個網址的清單時，那份清單直接成為內建清單（名稱、間隔與內容保留，不會有兩份）。停用的清單不下載也不套用；啟用、停用、新內容與復原刪除的內建清單都立即套用到執行中的連線（重新編譯 overlay，不換代）。**內建清單不涵蓋連線自己需要的位址**（WireGuard 端點與 DNS 伺服器）：內容由來源決定，以回報為主的清單可能列入 VPN 伺服器的位址，所以這些位址只從那條連線的 overlay 拿掉（記一行日誌），不拒絕這份清單、也不擋連線啟動；使用者自己的清單照舊，涵蓋時拒絕並寫明清單、連線與位址。每份清單（含使用者上傳與網址清單）匯入時都去掉私有與特殊用途位址（IANA 非全球可達的區段與其 NAT64 形式），數量記在 `special_filtered`，去掉後沒有內容的清單被拒絕——封鎖清單不能用來拒絕私網子網段，那要縮小安全設定允許的私網。自動封鎖預設開啟（門檻與驗證範圍不變）。新安全設定預選內建清單（API 建立時沒給 `blocklists` 仍是空的）。
- **轉入連線（port forward）**：`InboundGuard::admit(source)`（`crates/instance/src/inbound.rs`）先擋 IP 封鎖清單與封鎖中的來源，再以每來源的滑動視窗計數新連線，超過門檻就封鎖並回報 manager；追蹤的來源數與封鎖數都有上限，連線需要的對端與 DNS 伺服器不會被封鎖。封鎖由 manager 寫入 Store、到期刪除、新 generation 啟動時帶入；解除封鎖立即送到執行中的 worker，不會解除 IP 封鎖清單或基本規則。
- **Port forward（轉發）**：`ForwardBinding` 把一條連線的 tunnel port 接到同一條連線的**受管 App** 在本機監聽的 port。worker 的 Port Controller（`crates/instance/src/forward/`）在設定交付時就在 netstack 保留 tunnel port（出站 flow 不會拿到它），但只有在 manager 的 **lease** 還有效、且 payload gate 開啟時才監聽：gate 收緊時不收新連線、既有的保留（與代理埠相同），lease 撤銷或更換時立即 reset 這個 port 的所有連線。每條新的 TCP 連線或 UDP flow 依序經過：證據（來源不在 tunnel 自己的網段、也不在私有／特殊網段 → 記為「外部連入」）、gate 與 lease、`InboundGuard::admit`（IP 封鎖清單、封鎖、自動封鎖）、轉發的連線上限，最後才由 `AppEndpoint` 連到 lease 指定的本機位址——worker 唯一的 host 端連線（§8）。UDP 每個遠端位址一條 flow（自己的 loopback socket，connect 到 App），數量有上限、60 秒閒置結束。lease 由連線的 actor 簽發（`crates/instance-manager/src/forwards.rs`）：每次 App 狀態變化、每次 App 監看（2 秒）之後與至少每 5 秒，核對 App 正為這條連線執行、它的程序樹在 127.0.0.1／::1 或萬用位址持有目標 port（TCP 監聽、UDP 綁定），且只持有萬用位址時沒有本使用者的其他程式占用本機位址（更具體的 bind 會搶走連線）；不符就撤銷。狀態 `disabled → connection_not_ready → target_missing → target_not_owned → listening` 依序判定，`listening` 要 worker 回報以該 lease 監聽才算；外部可達只有真的觀測到外部連入才是 `observed`（附時間，存在 Store，連線與 tunnel port 不變時跨重啟保留）。Mullvad 連線不帶轉發（顯示原因、儲存時拒絕）。嚴格隔離（Linux netns）的連線也帶轉發：worker 在 sandbox 內以 kernel socket 在 tunnel 位址監聽，TUN 的封包過濾只在轉發的 listener 開著（lease 有效、gate 開啟）時放行新的轉入連線與資料報（保留中但沒有監聽的 TCP port 回 reset），來源同樣經 `InboundGuard`；`AppEndpoint` 連的是 sandbox 自己的 loopback；manager 判斷是否有別的程式搶得到該位址時，只算 App 網路命名空間裡（或命名空間不明）的程式。轉發 relay 的位元組是連線的 payload（2026-11-07）：每個轉發照舊計自己的 `bytes_in`／`bytes_out`，同時加進這一代所有轉發共用、只增不減的合計（`PortController::relayed`，轉發移除後它的位元組仍留在合計裡；直接送進沙箱的 UDP 不在其中，那由封包過濾算進 App 沙箱），worker 以 `WorkerStatus.forward_rx_bytes`／`forward_tx_bytes` 回報，與代理埠的 payload 一起構成連線的 payload（§4.3、§6）。在這之前轉發的流量沒有計入任何 payload：正式安裝上一個 P2P App 的 BitTorrent 大多經轉入連線下載（一個 generation 1.54 GB），總覽、App 與數據統計卻接近 0 bps。
- **把來源位址傳給 App（PROXY protocol v2，選用，2026-11-06）**：worker 一律從 loopback 連到 App（strict 是 sandbox 的 `127.0.0.1`），App 看不到真正的對端，P2P 程式卻要靠它（eMule 的 HighID 檢查與對端身分、BitTorrent 的 peer 身分；實際的 P2P 用戶端丟掉不可路由的來源，正式安裝上一個 eD2k 轉發收了 152 條連線、`bytes_out` 是 0）。轉發開啟 `proxy_protocol`（`ForwardBinding`／`ForwardInput`，預設 `false`）時，worker 連上 App 之後、轉送任何位元組之前，先在這條 TCP 連線寫一個 PROXY protocol v2 標頭（HAProxy `proxy-protocol.txt` §2.2：12 位元組簽章、`0x21`＝v2 PROXY、`0x11` TCP/IPv4 或 `0x21` TCP/IPv6、來源位址、目的位址、來源 port、目的 port，沒有 TLV；IPv4 28 位元組、IPv6 52 位元組；`crates/instance/src/forward/proxy.rs`）。來源是 tunnel 上看到的遠端（IPv4-mapped 位址當 IPv4），目的是這條連線的 tunnel 位址與轉發的 tunnel port（netstack 與 strict 的 kernel socket 都從接受的連線讀本端位址）。標頭要在 App 的連線時限（5 秒）內整個寫出，否則這條連線結束；它不是 payload，不算進 `bytes_in`／`bytes_out`。只用於 TCP：UDP datagram 照原樣轉送，只轉發 UDP 的轉發不能開啟（`FORWARD_PROXY_PROTOCOL_TCP_ONLY`，`/proxy_protocol`），`both` 只在 TCP 連線上加。改這個設定和改其他欄位一樣讓轉發重新開始：既有連線結束，新的連線從第一個位元組起照新的設定。App 必須支援並開啟 PROXY protocol v2，否則它的連線會失敗；誰能送這個標頭見 §8 第 13 條。設定在網頁轉發對話框（「把來源位址傳給 App」）、inspector「設定」的「來源位址」、`vpnctl forward status` 與 `vpnctl forward proxy-protocol <轉發> on|off`；worker 的 `ForwardSpecWire.proxy_protocol` 缺少時（較舊的 manager）當作關閉。
- **UDP 直接送進沙箱（選用，只限嚴格隔離，2026-11-06）**：PROXY protocol 只解決 TCP；UDP 從 loopback 轉送時，App 看到的每個 datagram 都來自 sandbox 的本機位址，而 eMule 的 Kad、BitTorrent 的 DHT 要靠每個 datagram 真正的來源位址路由並回覆（正式安裝上的 P2P 用戶端一直回報 Kad UDP-firewalled，雖然供應商已把公開 port 的 TCP＋UDP 轉到這條連線）。逐 datagram 的 PROXY 標頭沒有 App 會讀。轉發開啟 `udp_direct`（`ForwardBinding`／`ForwardInput`，預設 `false`）時，UDP 不經 worker：worker 不保留、不綁定、不轉送這個 UDP port（TCP 照舊保留並轉送，PROXY protocol 照舊只加在 TCP），而是向 strict 封包過濾登記一個**直接 port**（`DirectUdpPort`，`crates/tunnel/src/strict/filter.rs`）；App 自己在 sandbox 裡綁定 `0.0.0.0:<port>`（或 tunnel 位址）的 socket 原樣收到 datagram、看到真正的來源，並從同一個 port 回覆。過濾只在轉發的 lease 有效（`DirectUdpPort::open`，lease 結束即關）、gate 開啟時才讓**新的**遠端進來，而且每個新遠端先經轉發的 `DirectUdpPolicy`（`crates/instance/src/forward/direct.rs`）：與轉送的 UDP 相同的順序與判斷——外部連入證據、`InboundGuard::admit`（IP 封鎖清單、自動封鎖、封鎖數上限時的拒絕）、轉發的同時連線上限（`max_connections`，計算追蹤中的 flow）；其餘一律丟棄並記在轉發的計數（guard 與上限的 `refused_*`；沒有 lease 或 gate 收緊（probe）時 `refused_closed`，gate 關閉或 sealed 時什麼都進不來、只算在過濾的丟棄數；表滿時 `udp_dropped`）。admit 之後這是一條 App 的 UDP flow，存在過濾的 App flow 表、帶著轉發的標記：之後的 datagram 只查表、不再判斷（熱路徑上只有新遠端才呼叫 guard）；App 的第一個回覆讓它成為「已回應」（遠端起始的 flow 由 App 回應，與 App 起始的相反），之後依 conntrack 的時限保留（§4.3）；App 在這條 flow 上的 datagram 不經目的地政策（如同轉送的回覆）。轉發的 flow 在 lease 結束、轉發改變或停用、換代時立刻忘記，下一個 datagram 又是不請自來；封鎖清單或封鎖套用時與其他 App flow 一起忘記，下一個 datagram 重新經 guard。App 自己從同一個 port 送出的 flow（Kad 的查詢）是 App 的 flow，不屬於轉發、不受它影響。轉發的計數照常有意義：`accepted`（admit 並開始追蹤的 flow）、`udp_active`（追蹤中的轉發 flow）、`bytes_in`／`bytes_out`（這些 flow 經 TUN 的 UDP payload，分段的 datagram 也完整計入；它們同時是 App 沙箱的流量）。條件（API 與網頁都檢查）：轉發要有 UDP（`FORWARD_UDP_DIRECT_NEEDS_UDP`）、App 的 port 等於 tunnel port（沙箱內不轉換位址，`FORWARD_UDP_DIRECT_SAME_PORT`）、連線是嚴格隔離（`FORWARD_UDP_DIRECT_NOT_STRICT`）、目標 App 是嚴格隔離（`FORWARD_UDP_DIRECT_APP_NOT_STRICT`），都在 `/udp_direct`。manager 核對 App 的程序樹在 tunnel port 以所有位址或非 loopback 位址（sandbox 裡只有 tunnel 位址）持有 UDP、沒有其他程式在這種位址持有它（`PORT_SHADOWED`／`PORT_HELD_BY_OTHER`），只在 127.0.0.1 持有時 `APP_UDP_LOOPBACK_ONLY`，App 不是嚴格隔離時 `UDP_DIRECT_NOT_STRICT`；lease 不帶 UDP 位址（worker 不連 App 的 UDP），目標顯示 App 持有的位址（例如 `0.0.0.0:24680`）。所以同一個 port 的 TCP＋UDP 轉發，App 要在 127.0.0.1 監聽 TCP、在 0.0.0.0 接收 UDP。沒有 sandbox 的連線（例如之後關掉嚴格隔離）上，這個轉發的 UDP 完全不轉送——不會改回從 loopback 轉送——狀態寫出原因，TCP 照舊。設定在網頁轉發對話框（「UDP 直接送進沙箱」）、inspector「設定」的「UDP」列、`vpnctl forward status` 與 `vpnctl forward udp-direct <轉發> on|off`（只轉發 TCP 的轉發要加 `--add-udp`，在同一次儲存把協定改為 TCP＋UDP），改變它和改其他欄位一樣讓轉發重新開始；`ForwardSpecWire.udp_direct` 缺少時（較舊的 manager）當作關閉。安全性見 §8 第 15 條。

### 4.2 macOS

Gateway（explicit proxy）完整可用、不需 root。App 隔離提供兩級，UI 誠實標示：
- `proxy_env`：只設定代理環境變數，**不保證**App 所有流量走 VPN。
- `enforced_proxy`：以 Seatbelt profile 拒絕該 App 除了自己 Gateway loopback port 以外的所有網路。這是可觀測、可測試的 OS 強制，但 Apple 未把 `sandbox-exec` 列為穩定 API，所以標為「強制代理（Seatbelt）」而不是「完整 App 隔離」。
  - 擋不住的部分（macOS 26.6 實測）：`(local tcp "localhost:*")` 不精確，App 可以在 `0.0.0.0` 甚至區網位址監聽；`network-inbound` 在 `listen()` 時判斷、還沒有對端，`(remote …)` 篩選放在 allow 會讓所有 `listen` 失敗、放在 deny 永遠不成立，所以區網連入一定會被 accept。manager 因此每 2 秒檢查程序樹的所有 TCP socket：非 loopback 的監聽（`APP_LISTENER_NOT_LOOPBACK`），或本端位址是非 loopback 的連線（從網路連入；App 除了 127.0.0.1 的 Gateway 連不出去，`APP_CONNECTION_NOT_LOOPBACK`）都會讓 App 停止。這是偵測不是預防：兩次檢查之間開啟又關閉的連線看不到。
- 程序樹＝根程序的子孫、根程序的程序群組，加上帶有該次執行標記的程序，所以 double fork＋`setsid` 脫離的程序（`ssh -f`、`aria2c --daemon`）停止時仍找得到：Seatbelt 執行的 profile 拒讀 App 暫存目錄裡的一個標記檔、允許它的同層檔案（兩個檔案由 manager 建立，App 不能改寫），`sandbox_check` 據此找出該 profile 下的每個程序（sandbox 會繼承、無法離開）；每個 App 的環境都有保留的 `VPNM_RUN=<run id>`（Linux 讀 `/proc/<pid>/environ`；macOS 不提供其他程序的環境）；Linux 的 App cgroup 成員一律算進樹。沒有可靠標記時（`proxy_env` 且沒有 cgroup），App 結束的狀態會說無法排除仍有程序在執行，不宣稱已全部結束。
- Linux 的 App 身分是 pid＋開機以來的 start ticks（不受時鐘跳動影響），執行紀錄另記 boot id；別次開機的紀錄直接視為已結束。
- NetworkExtension 強制隔離需要 Developer ID 與 entitlement，目前沒有 → capability 回報 `blocked`，不偽裝完成。

### 4.3 Linux

除了與 macOS 相同的 explicit proxy 路徑外，提供 **rootless strict 模式**：以非特權 user namespace 建立私有 **netns＋mount ns**，netns 裡只有 `lo` 與 TUN；WireGuard UDP socket 在進 namespace 之前於 host namespace 建好（WireGuard 官方描述的作法）。整個過程**不需要 root、不改 host 路由／DNS／firewall**。在 user namespace 受限的系統（例如 Ubuntu 24.04 的 AppArmor 限制）回報 `blocked` 並說明原因。

- **netns 擋不住 pathname UNIX socket**：App 仍可能經 systemd-resolved／nscd 讓 host 代查 DNS、連到 D-Bus 拿 Secret Service、甚至連 `manager.sock`。所以 mount ns 以私有 tmpfs 遮蔽 `/run`、`/var/run`、`$XDG_RUNTIME_DIR`、本產品 state dir，並掛上指向 netns 內 DNS listener 的私有 `resolv.conf`（abstract UNIX socket 本身隨 netns 隔離）。
- **sandbox 跨 generation 存活**：ns 與 TUN 的 FD 由 manager 持有（`SandboxLease`，以 instance＋sandbox_epoch 命名），worker 換代時交給新 worker；受管 App 留在原 sandbox 離線等待，不會被困在沒有 TUN 的舊 netns。只有 sandbox 本身無法證明完好時才終止 App tree、建新 sandbox。
- **strict 模式只用 kernel stack**：worker 在 netns 內用一般 kernel socket 做 Gateway／DNS 外連（TUN↔GotaTun），不與 smoltcp 混用同一個 tunnel 位址，避免埠衝突與 kernel 對 smoltcp 連線回 RST。
- **實作（2026-10-27，在 Linux 桌機實測）**：Instance 的 `strict` 開關（只在 Linux 接受；macOS 回 `STRICT_UNSUPPORTED`）。sandbox 由 `vpnd sandbox-holder`（`crates/platform/src/sandbox`）建立：holder 是 sandbox pid namespace 的 pid 1、不可被 ptrace，持有 TUN、DNS listener（127.0.0.53:53，由 holder 綁定，worker 不需要任何 capability）與 namespace；以 rendezvous socket（`run/sb-*.sock`）讓重啟後的 manager 核對 installation／boot／pid＋啟動時間後收養。manager 建立（`Setup`）或收養（`Attach`）sandbox 時把自己程序的 pidfd 交給 holder：manager 的連線還在、或那個 manager 程序還活著，sandbox 都算有人管理；連線不在、而且 manager 程序也已結束，超過 10 分鐘才自行關閉（2026-11-07；之前只看連線：manager 還在執行、只是一條連線的 actor 結束〔panic，帶走它的 `SandboxLease`〕時，10 分鐘後 sandbox 與其中的 App 就被關掉——一台遠端主機升級前發生，舊版在磁碟寫滿時任何寫日誌的工作都會 panic）。較早版本的 manager 不送 pidfd，holder 照舊只看連線。連線的 actor panic 時，manager 1 秒後（啟動不到 60 秒就失敗的，30 秒後，不會原地打轉）換上新的 actor，經 rendezvous socket 收養同一個 sandbox、啟動新的 worker 世代，App 不中斷；之前要等到使用者再啟動這條連線才補上。holder 自己結束時（被系統結束、記憶體不足、當掉；2026-11-11）：它是 pid namespace 的 pid 1，裡面的 App 跟著結束，而 worker 不在那個 pid namespace 裡、照常收送，再也沒有東西能在那個 sandbox 裡啟動。連線的 actor 以 holder 的 pidfd 得知（`SandboxLease::holder_gone`，`actor.rs` 的 `on_holder_gone`）：立刻放掉那份 lease（App 不會被送進已死的 sandbox），有 worker 在跑就結束這一代（`SANDBOX_LOST`），下一代建立 epoch 更高的新 sandbox，設了自動恢復的 App 跟著回來；沒有 worker 時直接重建。之前要到連線下一次啟動才會發現，期間 App 一律啟動失敗。manager 已經在停止時不重建（`ensure_sandbox` 回 `MANAGER_STOPPING`）：整組程序同時收到訊號時（在終端機對 dev stack 按 Ctrl-C），holder 自己先關閉 sandbox 並結束，manager 還在等 App 停止，之前會在這時建出一個沒有人管的新 sandbox，10 分鐘後才自己關閉；正式安裝（systemd `KillMode=mixed`，只有 manager 收到 SIGTERM）不會遇到。遮蔽目錄另含 `/tmp`、`/var/tmp`、`/dev/shm`（X11、tmux、瀏覽器 singleton 等 pathname socket 多在這裡），`/proc` 換成 sandbox 自己的（否則 `/proc/<host pid>/root` 能繞過遮蔽）。worker 以 setns 進入 sandbox 的 user＋network namespace、丟掉全部 capability；啟動前確認 namespace 只有 `lo` 與 TUN。TUN 上每個封包過濾：來源必須是 tunnel 位址、特殊目的地丟棄、App 新 flow 需 gate open 與 `DestinationPolicy` 同意（probe 時既有 flow 繼續）、拒絕時回 TCP RST／ICMP administratively prohibited、外部主動連入除了正在監聽的轉發 tunnel port 與轉發 lease 有效的直接 UDP port（§4.1）一律丟棄、換代／Stop 時 App 的 TCP 兩端都送 RST（對端還沒回應的連線也包括在內）。App 的 flow 依狀態保留，從最後一個封包算起，與 Linux conntrack 相同：UDP 還沒有回應 30 秒、有回應之後 2 分鐘；TCP 對端還沒回應（送出 SYN 沒等到 SYN-ACK——P2P 撥號多半如此——或上一代留下、中途接手的連線）2 分鐘，建立後 2 小時 4 分，一個方向送出 FIN 之後 2 分鐘，雙向 FIN 或 RST 立即結束（2026-11-06；之前所有 UDP flow 一律 2 分鐘、所有 TCP 一律 2 小時 4 分，正式安裝上的 P2P App 停在 UDP 上限 4096 條，新的 DHT／Kad 查詢一律被拒）。UDP 與 TCP 各最多 65 536 條；新 flow 遇到表滿時，先清掉已過期的（全表清理最多每秒一次，不會每個封包掃一次表），再淘汰最久沒有活動、而且對端還沒回應的 flow，只有表內每條都已經得到回應時才拒絕新的（RST／ICMP，即 conntrack 的 early drop）；對端還沒回應的 flow 依最近活動排序存放，過期與淘汰都不必掃表。淘汰與因表滿而拒絕都有計數（`SandboxWire.evicted`、`table_full`，顯示在 App inspector）。對已經回應過的連線 port 再送 SYN，視為新的連線重新開始。轉發的直接 UDP port（§4.1）收進來的 flow 也在同一個 UDP 表、同樣的時限與淘汰，只是方向相反：由遠端起始、App 的第一個回覆才算回應；它帶著轉發的標記（轉發計數它的 flow 與 payload），lease 結束時一次忘記。封包過濾同時計算 App 的流量：App flow 經 TUN 的 TCP 段 payload 與 UDP payload，兩個方向分開（App 的資料報分段時，後續分段依第一個分段歸屬，兩個方向都追蹤）；和網卡計數一樣算的是經過的封包，重送的 TCP 段會再算一次。worker 自己的 flow（代理埠與 Provider 連線、DNS、轉發）不算——代理埠與轉發的 payload 在它們的 relay 計算（§4.1）——ICMP 與過濾自己寫出的 RST／ICMP 也不算，所以不會重複計算。連線的 payload＝代理埠＋轉發＋App 沙箱裡 App 自己的 flow（`WorkerStatus::apps_payload` 加上代理埠）。嚴格隔離的 worker 在 sandbox 的 network namespace 裡、只連得到 sandbox 的 loopback，轉發一律送到 sandbox 裡的 App，所以 App 沙箱的部分是過濾的計數加上轉發 relay 的位元組（`WorkerStatus::sandbox_payload`；2026-11-07 起），另外回報、保存（§6）並顯示在總覽、流量路徑、數據統計、效能統計與 App inspector（概況一列即時 ↓／↑，「流量」分頁細看）；沒有 sandbox 的連線這些值是 null（不是 0）。worker 自己的 socket 以 local port 登記（不設 SO_REUSEADDR／PORT，App 搶不到同一埠），只受 gate 約束。SOCKS5 UDP relay socket 改由 manager 在 host namespace 綁好交付。封鎖清單 overlay 與 ban 更新時，worker 也會對 App 與自己通往新被拒目的地的 TCP 連線兩端送 RST、忘掉對應的 UDP flow（下一個 datagram 重新檢查）。受管 App（`AppIsolation::StrictNetns`）經 App supervisor 的 `SandboxProvider`（`vpn_platform::sandbox::AppBackend`）啟動：manager 直接啟動 `vpnd sandbox-app`（App 的根程序、manager 的 child，stdin `/dev/null`、stdout／stderr 寫 App log），交給它 sandbox 的 user／network／pid namespace；它在 sandbox 的 user namespace 內從 host 視角建立 App 專屬的 mount namespace（與 sandbox 相同的遮蔽，另遮 `~/.ssh` 等私有目錄；App 的 HOME、TMPDIR、工作目錄以 bind 保留在原路徑），再在 sandbox pid namespace 底下為這棵 tree 開巢狀 pid namespace：tree init 掛上自己的 `/proc`、丟掉全部 capability、不可 ptrace，App 以 `no_new_privs`、精確的 argv／env／cwd、只留 stdio 執行；App 結束時其餘程序 SIGTERM、5 秒後 SIGKILL，根程序以 App 的結束碼或訊號結束。寫入可以另外限制（`AppSpec.confine_writes`，2026-11-07）：啟動程序在 App 自己的 mount namespace 裡建 Landlock ruleset，App 在 `no_new_privs` 之後、`exec` 之前限制自己——處理 Landlock ABI 3 的所有寫入權限（寫入與截斷檔案、建立、刪除、連結與跨目錄改名），只在 `writable_paths`、它的 HOME、TMPDIR 與 `/dev` 底下允許；讀取與執行不受影響，已開啟的描述子（App log）照常寫入。核心沒有 Landlock 時 App 不啟動（不會不受限制地執行）。核心的 Landlock 比 ABI 3（Linux 6.2）舊時也一樣不啟動：ABI 1、2 擋不住截斷（`truncate(2)`、`O_TRUNC`），使用者能寫的檔案仍然可以被清空，不能算是限制了寫入位置（2026-11-11，`landlock.rs` 的 `refusal`）。停止時 SIGTERM 經 tree init 送給整棵樹，等 App 的停止前等待（`stop_grace_secs`，預設 10 秒）後強制時 SIGKILL tree init（整個 pid namespace 結束），manager 再以程序表確認；拆除 sandbox 時等這條連線的 strict App 裡最長的那個（至少 3 秒），holder 自己關閉 sandbox（收到訊號、沒有 manager）時最多等 900 秒、程序全部結束就關。Stop 與 Restart 的 API 最多等 20 秒就回答（App 仍在停止中），停止繼續進行，結果由 App 的狀態事件送出（控制呼叫 30 秒逾時）。strict 連線在未執行時也保有（關閉的）sandbox，讓 App 可以先啟動、等連線執行才上線。另有 `Manager::sandbox_spawn`／`SandboxLease::spawn`（由 holder 啟動，診斷用 `vpnd sandbox-exec` 也走這條）。復原（recovery）把 Instance 持有的 sandbox 列為擁有的資源；沒有 manager 持有、但能證明屬於本安裝的 sandbox 列為 `orphan_sandbox`，確認後先結束其中的 App 再拆除；沒有人接聽的 `sb-*.sock` 列為 stale socket。限制：GUI App 的 X11／Wayland／session bus 在 strict sandbox 內都不可用；家目錄等其他位置的 pathname socket 仍可達（由受管 App 的私有 HOME 處理）；systemd 停止服務時整個 cgroup（含 holder）會被結束，所以「manager 重啟收養」只在 manager 不經 systemd 重啟時發生；經 systemd 時 sandbox 與其中的 App 一起結束、下次啟動重建（App 是否重啟由受管 App 的啟動器依 `restart_on_recovery` 決定）。manager 的 unit 設 `KillMode=mixed`：停止時先只通知 manager，由它結束自己的 App 並保留執行紀錄，manager 結束後 systemd 才結束剩下的程序；若與 manager 同時收到訊號，App 可能先結束、被當成自行結束，升級或重開機後就不會再啟動（2026-11-02 在 Linux 桌機升級時發生）。
- **本機存取埠（strict App，2026-11-02）**：strict App 的 `127.0.0.1` 是 sandbox 的，主機連不到。`AppSpec.access_ports`（`[{app_port, host_port, bind: loopback｜lan, allow: [CIDR]}]`）把 App 在 sandbox 內監聽的 port 開到這台主機：只限 `strict_netns`（其他模式回 `APP_ACCESS_STRICT_ONLY`，所以 macOS 沒有），每個 App 最多 8 個，兩個 port 都是 1024–65535 且不重複；`lan` 必須列出允許的網段（最多 32 個；`0.0.0.0/0`、loopback、群播、link-local 拒絕，公網網段只警告），`loopback` 不帶清單。manager 在主機的網路命名空間綁 `127.0.0.1:<host_port>`（`lan` 為 `0.0.0.0`），App 設定了就一直持有、不論 App 是否執行；儲存時拒絕已被代理埠、其他 App 的存取埠或其他程式占用的 port（`LISTENER_CONFLICT`），之後才被占用的在背景重試（1 秒起倍增到 30 秒）。每條連線在讀取任何資料前經 `vpn_platform::admission` 判斷（§8 第 12 條）；通過的以 SCM_RIGHTS 經 App launcher（`vpnd sandbox-app`）的控制 socket 交給 relay。relay 是 launcher 在 App 開始執行後 fork 的程序（加入 sandbox 的 pid namespace 之後 kernel 不允許再開 thread），在 sandbox 的 network 與 pid namespace（App 的巢狀 pid namespace 看不到它），以 `PR_SET_PDEATHSIG` 隨 launcher 結束，只留控制 socket 與 stdio、放棄全部 capability；它只連 App 這次執行設定的 App port（sandbox 的 `127.0.0.1`，被拒時試 `::1`），雙向轉送並保留 half-close，同時最多 256 條，從不監聽、不連其他位址。App 沒在執行（或這次執行還沒有這個 port）時連線被拒絕：HTTP client 收到 503 與原因，其他直接關閉（同時說明原因的最多 64 條）。允許清單、監聽位址與 host port 的變更立即生效；這次執行還沒有轉送的 App port 要重新啟動 App 才開放（`restart_needed`）。每個 port 的狀態（`unavailable`／`app_stopped`／`restart_needed`／`serving`、是否監聽、App 是否在 sandbox 內監聽該 port（每 2 秒）、manager 這次啟動以來的轉送與拒絕次數、最近的拒絕與錯誤）顯示在 App inspector 與 `vpnctl app status`。這條路徑不經 tunnel、不經目的地政策：位元組只在主機（或允許的區網）上的 client 與 App 之間往返，App 不能藉它連出去；App 看到的轉送連線都來自 sandbox 的 loopback。

### 4.4 資源上限與頻寬上限

- **頻寬上限（兩個平台）**：連線設定（`InstanceLimits.download_bps`／`upload_bps`，0.1 Mbit/s–100 Gbit/s）。worker 每個方向一個 token bucket，所有代理埠共用（`crates/instance/src/shaping.rs`，虛擬時間排程：等待者先到先過、長期速率精確、閒置後最多放行 50 ms 的量）。TCP 中繼在寫出前等待上限，等待期間不再讀取，背壓經 TCP 視窗傳回發送端——不丟資料、不改走其他路徑；HTTP 轉送的 body 以約 20 ms 的量分段放行；超過上限的 UDP 封包丟棄並計數——比整個 50 ms 量還大的封包（慢速上限下的完整 QUIC／RTP 封包）在 bucket 滿時放行，超出的量記為欠額，之後的 UDP 與 TCP 等它還清，長期速率仍是上限。DNS 與管理 connector 不是 payload，不計入。上限隨 `Configure` 生效（gate 開之前），之後以 `SetBandwidth`／`BandwidthApplied` 即時套用，不列入 `pending_changes`。worker 回報累計的等待時間與 UDP 丟棄數，即時速率換算成「區間內有多少比例的時間在等上限」。
- **Linux cgroup v2**：installer 的 manager unit 設 `Delegate=yes`。manager 啟動時確認委派：system manager 在 cgroup 上設 `user.delegate`／`trusted.delegate`；systemd 的 user manager 不設，所以 installer 的 unit 另以 `--delegated-cgroup` 告知，且只接受該 unit 自己的 cgroup（`*.service`／`*.scope`），把自己移進 `<unit>/manager`（cgroup v2 有 controller 的節點不能放程序），替 `<unit>/workers`、`<unit>/apps` 開啟 memory／pids／cpu，並移除空的殘留。每個 worker 在 `exec` 前進入 `workers/<instance>-<generation>`：`memory.max`＝連線緩衝＋256 MiB（程式與執行緒、IP 佇列、DNS 快取、最多 16 MiB 的封鎖清單 overlay 與換版時 24 MiB 的訊框、Gateway client 的 kernel socket buffer；嚴格隔離時另有封包過濾的 App flow 表，UDP 與 TCP 的表都曾全滿時最多約 33 MiB——嚴格隔離不用 netstack 的連線緩衝）、`memory.swap.max=0`、`memory.oom.group=1`、`pids.max`＝64＋每個 CPU 2。受管 App 每次執行一個 `apps/<app>`（使用者設定的記憶體、CPU％、程序數），根程序在 `exec` 前或啟動後立即加入（與隔離後端無關），watcher 每 2 秒把尚未在內的子程序移入。寫入後讀回 kernel 接受的值才回報；OOM 結束回報為 `WORKER_OOM_KILLED`／`APP_OOM_KILLED`。程序樹結束後移除 cgroup（App 的 cgroup 裡若還有程序，先以 `cgroup.kill` 結束）。這些上限防的是失控（洩漏、fork 迴圈），不是同一使用者的惡意程式：同 UID 的程序可以把自己移到其他可寫的 cgroup。
- **沒有委派或 macOS**：dev stack、終端機啟動的 manager 沒有委派的 cgroup；macOS 沒有 cgroup、不強制 `RLIMIT_AS`／`RLIMIT_DATA`，`RLIMIT_NPROC` 以使用者計算。這時記憶體、CPU、程序數上限回報 `unsupported` 與原因（`limit_memory`、`limit_cpu`、`limit_processes`），worker 狀態列出未生效的上限與原因；App 設定了無法執行的上限時，儲存與啟動都會被拒絕，不會無聲地不限制。開啟檔案數（`RLIMIT_NOFILE`，每個程序各自計算，`limit_open_files`）兩個平台都在 `exec` 前設定，Linux 另以 `prlimit` 依 pid 再設一次（任何後端都適用）。

### 4.5 傳輸設定

2026-11-10 新增：每條連線的緩衝、逾時與健康探測可以設定，有內建與自訂的設定檔可以選，也能依往返時間自動切換。之前每條 TCP 連線的緩衝寫死（送 256 KiB、收 512 KiB），而單一連線的速度上限是緩衝 ÷ 往返時間：往返 307 毫秒的雙層 VPN 路徑上，上傳最多 0.85 MB/s、下載 1.71 MB/s（實測下載 1.48 MB/s，貼著上限）。

- **物件**（`crates/domain/src/transport.rs`）：每條連線用一份傳輸設定（`InstanceSpec.transport: TransportRef`），沒有選擇時是內建的「自動」——之前存的連線沒有這個欄位，讀成它。內建設定是程式的一部分（`builtin_transports()`：自動、平衡〔原本的值〕、長距離／多跳、超長距離／雙層 VPN、大量連線、省記憶體、不穩定線路），唯讀、以代號引用，程式改版時跟著改，不進資料庫。使用者的設定是可共用的實體 `TransportProfile`（`/v1/transport-profiles`，entity `transport_profile`）：被連線或被自動設定的區間引用時不能刪除。
- **固定與自動**：固定設定是一組數值（`FlowSettings`：TCP 收發緩衝的起始與上限、壅塞控制 Cubic／Reno／BBR、Nagle、延遲 ACK、連線逾時、keepalive、無回應中止、UDP 緩衝）。自動設定為每個往返時間區間選用一份固定設定（`AutoBand`，1–6 個，由 0 毫秒起遞增）；區間不能選用自動設定，一份被區間選用的設定也不能改成自動，兩者在儲存時於 policy lock 下以已存的設定檢查。兩種都帶健康探測（`HealthSettings`：探測間隔、連續失敗次數、握手逾時）；自動設定用它自己的，不隨區間切換。manager 把引用全部解開成 `ResolvedTransport` 才交給 worker：worker 只看得到數值。
- **即時套用**：傳輸設定不屬於要重新啟動才套用的輸入，不列入 `pending_changes`。它隨 `Configure` 生效；之後連線或設定檔一儲存，actor 重新解析，結果不同就送 `SetTransport`（帶序號）：worker 之後建立的 flow 用新值、已建立的不動，健康探測的間隔與次數同時換。每秒的 `Status` 帶回它描述的序號、目前的區間、量到的往返時間與緩衝放大的次數，成為 `RunningInfo.transport`。一代的驗證期限是握手逾時＋15 秒，至少 30 秒。
- **往返時間與區間**（`crates/tunnel/src/transport.rs`）：每條經 tunnel 建立的 TCP 連線的握手時間是一次往返；取最近 16 次（10 分鐘內）的中位數，還沒有任何握手時用健康探測（DNS 一問一答）的時間。新的 flow 採用這個往返時間所在區間的值。離開一個區間往下要低於它的門檻兩成：往返時間停在邊界上時不來回切換。
- **緩衝用到才放大**（netstack）：連線以起始大小建立——這是它一建立就佔用的連線緩衝，容量（「TCP 實際最多幾條」）用它計算——之後收、送各自量測：一個往返時間內搬運的量達到緩衝的一半，就是緩衝在限制這條連線，加倍，到上限為止。量測至少平均 10 毫秒（應用程式一陣一陣地讀寫，瞬間速率不代表什麼），門檻用真正的往返時間算，所以近距離的快速連線不會放大：同樣的速率在短的往返時間裡只是緩衝的一小部分。放大只用 payload 預算的四分之三，剩下的留給新連線：新連線從不因為別人的緩衝變大而被拒絕。控制類 flow（DNS、探測）維持小的固定大小。放大由 vendored smoltcp 的第三個修補支援（`vendor/README.md`）：換成較大的儲存並保留內容（還沒被確認的資料、亂序到達的片段），並在 SYN 時就依上限宣告 window scale。
- **嚴格隔離**：worker 自己的連線用核心 socket，緩衝由核心調整；設定只決定它們的逾時、keepalive、Nagle 與壅塞控制。沙箱裡核心的 TCP 緩衝上限（`tcp_rmem`／`tcp_wmem` 的第三個值，每個 network namespace 各自一份）由 holder 依 manager 的要求調高到設定上限的兩倍（核心把自己的帳務也算在緩衝裡），**只升不降**：比核心預設小的設定什麼都不改。worker 沒有 capability，寫不了這些值；舊版的 holder 不認得這個要求，manager 依 holder 回報的身分（`tunes`）決定送不送。
- **BBR**（2026-11-10）：`CongestionControl::Bbr` 只有核心有。嚴格隔離的連線自己開的 TCP 連線以 `TCP_CONGESTION` 向核心要它（`crates/tunnel/src/strict/connector.rs`）；worker 沒有 capability，核心只在 `net.ipv4.tcp_allowed_congestion_control` 列出 bbr 時才給，被拒絕的連線沿用沙箱原本的壅塞控制、照常連線。smoltcp 沒有 BBR，選了它的設定在使用者態的連線上等於 Cubic。內建的「長距離／多跳」「超長距離／雙層 VPN」「不穩定線路」選用它；「超長距離／雙層 VPN」的緩衝上限同時改成送 8 MiB、收 16 MiB（嚴格隔離的沙箱是核心上限 16 與 32 MiB）。原因是實測：往返約 300 毫秒、掉包約 0.2% 的路徑上，核心的傳送端用 Cubic 時 5 輪有 4 輪只有 0.2–0.5 MB/s，BBR 5 輪都在 1.9–2.5 MB/s；速度到 10 MB/s 之後，接收端的 16 MiB 上限成了下一個限制（傳送端有 2.4% 的時間在等接收視窗）。BBR 決定的是**送出**的方向：下載快不快看對方的核心。
- **實際用的壅塞控制**（2026-11-11）：設定要求的與實際在跑的可以不同，狀態把後者回報出來（`TransportStatus.congestion`：`in_use` 與 `fallback`，在 `RunningInfo.transport` 裡）。使用者態的連線一開始就知道：要求 BBR 時是 `cubic`、`fallback` 是 `userspace_stack`。嚴格隔離的連線每開一條自己的 TCP 連線，就以 `TCP_CONGESTION` 讀回核心實際給的名稱，狀態帶的是最近一條的答案；與要求的不同時 `fallback` 是 `kernel_refused`，還沒開過自己的 TCP 連線時整個欄位是 null（尚未確認）。它只及於連線自己開的 TCP 連線（代理埠的對外連線、DNS、探測）；嚴格隔離 App 自己的 socket 用沙箱 network namespace 的設定，不在內。`vpnctl instance inspect` 的「傳輸設定」一行與網頁連線檢視「設定」分頁的傳輸設定說明，在兩者不同或非預設時寫出來。
- **限制**：smoltcp 的傳送端遇到掉包恢復得慢（不使用對方的 SACK，逾時後整段重送），有掉包的路徑上限制上傳的是它，不是緩衝：這時量到的用量到不了緩衝的一半，緩衝不會放大，放大也沒有用。測試線路上（往返 30 毫秒、每 509 個封包掉 1 個）24 MiB 花了 75 秒，約每個往返 10 KiB。這種路徑要快，改用嚴格隔離（核心的 TCP）。
- **實機量測（2026-11-10）**：雙層 VPN 的內層連線，往返 306 毫秒，「自動」選用「超長距離／雙層 VPN」。一條連線下載 50 MB 從 1.53 MB/s（固定 512 KiB，貼著上限）到 8.9 MB/s。上傳只到 1.6 倍（固定 256 KiB 0.12 MB/s、最多 4 MiB 0.19 MB/s，交錯三輪的中位數），就是上一點的限制。同一條連線改成嚴格隔離後，上傳是 2.29 MB/s 對 0.58 MB/s（交錯三輪的中位數），沙箱的核心上限是接收 16 MiB、送出 8 MiB。
- **雙層 VPN 的 MTU**：連線走在另一條 WireGuard 連線裡面時，兩者都用預設的 1420，每個滿載的封包加上 WireGuard 的 60 位元組後是 1480，進外層時被切成兩片。外層沙箱的核心計數器（`FragOKs`／`OutRequests`、`ReasmReqds`／`InReceives`）在量測期間顯示：送出的封包 40–43% 被切片，收到的幾乎全是碎片。內層 WireGuard 設定的 MTU（設定檔可以編輯的欄位）要不大於外層 MTU 減 80；經 Mullvad 多跳實測，收的方向更窄（1380 位元組仍被切片，1360 不會），所以內層用 1280。切片與重組都發生在外層，內層的 VPN Manager 看不到，不會自己調整。量到的速度差別不明顯（交錯五輪），改的理由是外層少送一半的封包。

## 5. 控制面與生命週期

### 5.1 持久意圖與 generation

- Store 保存每個 Instance 的 `desired_state`（running/stopped）、`manual_stop`、`emergency_latched`、`intent_revision`。只有使用者操作（以及首次 Provider bootstrap 的授權子操作）會改變意圖；故障不會。
- 有未確認的停止（見 §5.3）時，Start 一律寫入新的意圖版本（`ConfirmStart`）：否則已存意圖本來就是 running，Start 不寫任何東西，下次重啟又會被擋下。
- 每次啟動配置新的 `generation`（單調遞增）並租用 identity lease（WireGuard 公鑰指紋全域唯一，同一把金鑰同時只能有一個存活 worker）。
- worker 換代 = 新程序。**「舊程序已死」以 per-key flock 為證據**：worker 在使用金鑰前取得 `locks/<key 指紋>.lock` 的排他 flock 並持有到結束；kernel 在程序死亡時自動釋放。manager 崩潰後舊 worker 可能被 launchd／init 收養而無法 reap，新 worker 拿不到鎖就不會啟動 tunnel（manager 依記錄的 pid＋啟動時間終止它）。worker 另外監看 parent：socketpair EOF 或 parent 變成 1 就立即結束。
- **升級安全**：binary 安裝在版本化路徑、不原地覆寫；manager 啟動時固定自己的執行檔，所有 IPC 第一則訊息互換 protocol 版本與 build-id，不相符就拒絕，避免舊 manager 叫起新版 worker。

### 5.2 啟動序列

1. manager 在 Store 交易內：檢查意圖仍為 running 且無 latch → 新 generation＋identity lease＋operation。交易內沒有任何網路或 OS 等待。
2. Platform 保留 listener（Gateway 的 `127.0.0.1:port` 由 manager bind 並在換代間持續持有，port 不會在重連期間被別的程序搶走）。kernel 即使沒人 accept 也會完成 TCP 握手放進 backlog，所以**沒有 worker 時由 manager 對這些 listener 跑 accept-and-reject**（SOCKS5 回 `0x02`、HTTP 回 503「VPN 重新連線中」），client 立即得到明確錯誤，不會卡住或在新 worker 起來後才處理過期請求。
3. spawn `vpnd instance`，經私有 socketpair 送 `Configure`（profile、DNS、Gateway、forward、policy，金鑰只在這條 channel 上傳一次），listener FD 以 SCM_RIGHTS 交付。
4. worker 建 GotaTun＋netstack，gate=closed；完成握手回 `TunnelObserved`，DNS 探測成功回 `DnsObserved`。
5. manager 核對同一 generation 的證據後送 `Activate{permit}` → gate=open → `Ready`。這是**唯一**開通點。
6. 任一步失敗：gate 保持 closed，程序結束，進入退避重試。

### 5.3 故障與恢復

| 故障 | 立即效果 | 恢復 |
|---|---|---|
| controller 崩潰／升級 | 無（tunnel 與 Gateway 照常） | 重連 manager 讀快照，不重播任何操作 |
| worker 崩潰、GotaTun fatal、DNS 必要健康失敗 | 該 Instance 的 Gateway port 仍由 manager 持有但拒絕連線 | manager 以 1/2/4/8/16/30s full-jitter 退避重建新 generation；5 次後冷卻 60s 再繼續，永不放棄、也永不直連 |
| 設定使它無法啟動（沒有 DNS、設定檔無效、WireGuard 金鑰正被另一個 Instance 使用） | 不計時重試，狀態寫出原因 | 儲存相關的連線、WireGuard、DNS 或安全設定後自動再試；金鑰被占用時，持有者停止或刪除後也會再試（變更計數的 watch，沒有輪詢）。只在使用者仍要它執行時才試，Stop 與急停不受影響 |
| peer 暫時無回應 | 內層 watchdog 停收新連線（gate→probe），既有 flow 保留；tunnel 持續重試握手 | 主動 probe 恢復 → manager 重新 Activate；逾限才換代。gate 未開啟時（驗證新的 generation 或已降級），失敗的 probe 2 秒後重試，不等平常 30 秒的間隔，所以新 generation 的第一次 probe 剛好失敗時，不會拖到 30 秒的啟動逾時再換代 |
| 對端的 port 回 ICMP port unreachable（對端程式結束） | 嚴格隔離的底層 socket 是 connected socket，GotaTun 收到 ECONNREFUSED 就結束接收迴圈 → `TUNNEL_FATAL`，以退避重建；代理埠模式的 socket 沒有 connect，收不到這個錯誤，要等 watchdog 降級 | 兩者都 fail closed；行為差異已由 Linux 擷取測試觀察到 |
| manager 活著但不回應（例如 macOS mbuf 耗盡時一個回覆寫不出去） | controller 與 manager 之間任一半斷掉就關閉整條連線並重連；controller 每 15 秒以 `System` 呼叫檢查存活（15 秒內要回答）；manager 寫不出回覆就關閉那條連線；送不到 worker 的訊息會結束那個 worker（fail closed） | manager 內有獨立 OS 執行緒的 watchdog，每 20 秒以 controller 相同的握手＋`System` 檢查自己的 `manager.sock`（10 秒上限），連續 3 次失敗就記錄並以結束碼 76 結束，由 launchd（KeepAlive、SuccessfulExit=false）或 systemd（`Restart=on-failure`）重新啟動；啟動後 60 秒內與停止中不計 |
| manager 正常停止 | 從停止的第一刻起，每個呼叫都得到可重試的 UNAVAILABLE（503，寫明「這個操作沒有執行，也沒有記錄」），不再啟動任何 actor；這時按下的急停不會被記錄，連線隨下一個 manager 依已存意圖回來 | launchd／systemd 依服務定義再啟動 |
| manager 崩潰 | worker 偵測 socketpair EOF 立刻自行結束（fail closed） | launchd／systemd 重啟 manager，依 Store 意圖重建。若有停止還沒確定寫入意圖（`pending-stops/` 裡有標記，或有比最後一次意圖寫入更新的停止 operation），該 Instance 不啟動、不配置 generation，狀態為 `recovery_required`（`STOP_NOT_CONFIRMED`）。使用者確認停止（急停則維持或解除急停），或明確 Start（`ConfirmStart`）後才解除 |
| Store 寫入失敗 | 新的持久操作被拒；既有 tunnel 繼續 | 恢復後對帳 |
| 使用者 Stop／急停 | 封鎖、停止標記與 latch 寫入**同時**開始：封鎖不等 DB。標記是 `<state>/pending-stops/<instance id>`（0600，先寫暫存檔、fsync、改名，再 fsync 目錄；macOS 用 `F_FULLFSYNC`）。latch 走不排隊的優先寫入路徑（macOS 開 `fullfsync`），**確實落盤**才回報 durable 並刪除標記；失敗時 UI 顯示「持久化待完成」並持續重試。正常結束時，每個未落盤的 latch 再試一次（最多 2 秒），仍失敗就保留標記。沒有「乾淨結束」旗標：啟動時只要有證據就不信任已存的 running 意圖 | 不自動解除；只有使用者明確 Start／解除急停 |
| 開機 | 所有 Instance 先為 closed | 只恢復 desired=running、無 latch、也沒有未確認停止的 Instance；標記放在保存資料的目錄（不放 Linux 開機就清空的 runtime 目錄）。`pending-stops/` 存在卻讀不到時 manager 不啟動（fail closed） |

- **執行中設定與已存設定**：generation 啟動時記下 worker 實際用到的設定指紋（連線的設定引用與上限、WireGuard 的金鑰參照與 peer、DNS 解析設定、安全規則；不讀任何秘密）。之後每次儲存都重新比對，結果放在 `running.pending_changes`，UI 據此說明哪些變更要重新啟動才會套用。改名、地點與到期日不會出現在這裡。
- **暫時性的緩衝不足（ENOBUFS）**：IPC frame、SOCKS5／HTTP relay、UDP ASSOCIATE、轉發、connector 與 `vpnctl ssh-proxy` 遇到 ENOBUFS 時等待重試（1 ms 起倍增到 50 ms），30 秒沒有任何進展才算失敗；WireGuard 底層 UDP 送不出時記為丟棄一個資料包（`tx_dropped`），裝置照常運作。代理埠與轉發的 loopback socket 固定 128 KiB 緩衝，避免大量連線在 macOS 上耗盡核心網路記憶體（連線建立時已宣告的 window 無法再縮，所以每條 loopback 連線仍約 640 KiB）。
- **代理埠**：建立或修改 Gateway 時，manager 會試綁 127.0.0.1 上的 port，被其他程式占用就拒絕（停用中的 Gateway 不綁，所以不檢查）；不論是否啟用，都不能用 App 本機存取埠的 port（§4.3）。`GET /v1/ports/free?from=` 由 manager 回答第一個沒有被代理埠或存取埠設定、而且在 127.0.0.1 與 0.0.0.0 都綁得到的 port；controller 從不綁定或連線。
- **Provider 到期日**：只用於顯示，不擋啟動——帳號真的到期時，供應商會拒絕握手，tunnel 照樣 fail closed。重新整理帳號時，從該帳號建立的設定檔會一併更新到期日。

### 5.4 watchdog 分工

- 內層（worker 內）：GotaTun fatal、主動 probe（經 tunnel 的 DNS 查詢；idle 時 WireGuard 本來就不握手，所以「握手年齡」不能單獨當故障訊號）、netstack 健康 → 只能**收緊**（停收新連線、回報 Fatal），不能自己開。
- 外層（manager 內）：程序存活、心跳、啟動逾時、資源上限 → 決定重建。兩層不互相搶著 restart。

### 5.5 安裝、升級與移除（installer）

安裝不屬於執行中的系統，而是獨立元件 `crates/installer`（`vpn-installer`）。

- **打包**：`scripts/package.sh` 依序建置前端、release 版 `vpnd`／`vpnctl`，再把兩者嵌入 `vpn-installer`，產生單一檔案 `dist/vpn-installer-<版本>-<os>-<arch>`（附 `.sha256`）。在目標平台上打包（macOS 打 macOS、Linux 打 Linux）。
- **發布與一行安裝**（2026-11-11）：推送版本標籤 `v<版本>`（必須等於 `Cargo.toml` 的 workspace 版本）時，`.github/workflows/release.yml` 在四個平台各跑一次 `scripts/package.sh`——Ubuntu 22.04 的 x86_64 與 aarch64（執行時需要 glibc 2.35 以上）、macOS 的 Apple silicon 與 Intel（`MACOSX_DEPLOYMENT_TARGET=11.0`）——把安裝檔與 `.sha256` 放進**草稿** release；公開的 repo 另外產生建置來源證明（`gh attestation verify`）。草稿要由人公開，這一步不自動。`scripts/install.sh`（`curl -fsSL …/scripts/install.sh | sh`）只看已公開的 release：以 release 頁的「latest」轉址得到版本（或 `--version`）、依 `uname` 組出與 `package.sh` 相同的檔名、只經 HTTPS 下載安裝檔與 `.sha256`、SHA-256 不符或不是 64 個十六進位字元就停止，相符才執行 `vpn-installer install`，其餘參數原樣交給它；整個腳本包在最後一行才呼叫的函式裡，下載到一半不會執行。它不需要 root、不寫暫存目錄以外的地方。workflow 引用的 action 都釘在版本對應的 commit。
- **授權聲明隨安裝檔走**（2026-11-14）：`scripts/package.sh` 在建好 `vpnd`、`vpnctl` 之後執行 `scripts/third_party_notices.py`，依 `Cargo.lock`（這個平台、三個程式實際用到的 crate，不含只給測試用的）與 `web/pnpm-lock.yaml`（production 相依）寫出第三方聲明：每個套件的版本、授權與來源，MPL 套件（GotaTun）的原始碼位置，修補過的 smoltcp，改寫進網頁的程式碼，以及各套件自己附的授權文字（相同的只列一次；沒有附檔的用標準文字）。這份文字內嵌在安裝檔裡（`vpn-installer licenses` 印出），也放在 `dist/<安裝檔>.notices.txt`，release 一併上傳。專案自己的授權是 MIT 或 Apache-2.0（`LICENSE-MIT`、`LICENSE-APACHE`、`NOTICE`）；AirVPN 轉接器（`crates/providers/src/airvpn` 與它的測試，每個檔案開頭有 SPDX 標示）例外，是 GPL-3.0-or-later（`LICENSE-GPL-3.0`），因為它是參照 Eddie 的原始碼寫的。`vpnd` 內含它，所以 `vpnd` 與安裝檔以 GPL-3.0-or-later 散布：這份聲明的開頭寫明這一點，授權文字的第一份就是 GPL 全文。
- **一個目錄**：VPN Manager 保存的一切都在同一個根目錄——macOS `~/Library/Application Support/VPN Manager`、Linux `$XDG_DATA_HOME/vpn-manager`（`~/.local/share/vpn-manager`）：`bin/`（`vpnd`、`vpnctl`、installer 自己的副本）、資料庫、`vault.key`、`gateway.key`、`logs/`、`pending-stops/`（未確認停止的標記，§5.3）、`installer/`（安裝紀錄 `state.json`、升級備份）。根目錄之外只有 supervisor 規定位置的服務定義；Linux 的 socket 在 `$XDG_RUNTIME_DIR/vpn-manager`。
- **Supervisor**：
  - macOS：使用者層 LaunchAgent（`gui/<uid>`）。不需 root，登入後自動啟動。label 為 `io.dennysora.ops.vpn-manager.<manager|controller>.<environment>.<instance>`（預設 `prod.main`），plist 在 `~/Library/LaunchAgents/`。只用 `launchctl bootstrap`／`bootout`（`load`／`unload` 幾乎所有失敗都回 0）；被停用的 label 先 `enable` 再載入。另外兩個選項都不採用：LaunchDaemon 需要 root；SMAppService 需要簽章的 .app。
  - Linux：systemd 使用者 unit `ops.vpn-manager.<component>.<environment>.<instance>.service`，在 `~/.config/systemd/user/`，`WantedBy=default.target`。lingering 關閉時由 installer 啟用，開機後不必登入也會執行。
- **重啟與停止**：兩個平台節奏一致——異常結束才重啟、不設放棄上限，原本穩定執行的服務很快就被拉起，連續崩潰時最多每 10 秒一次（launchd `ThrottleInterval`；systemd ≥254 以 `RestartSteps` 從 1 秒遞增到 10 秒，較舊版本固定 5 秒）；停止給網頁服務 30 秒、manager 960 秒（systemd `TimeoutStopSec`、launchd `ExitTimeOut`；2026-11-07）：manager 停止時先讓所有受管 App 同時收到 SIGTERM，各自等到自己的停止前等待（`AppSpec.stop_grace_secs`，1–900 秒）才 SIGKILL，全部結束就立刻退出——升級的停止也因此等得到錢包與資料庫存檔。manager 在 macOS 為 `Interactive`：它的 worker 承載使用代理埠的 App 流量，預設類別會被節流。
- **日誌**：由程式自己寫（`vpnd --log-file`）。supervisor 不設日誌路徑，也不送 journal（launchd 在日誌目錄被刪時會拒絕啟動 job）。stderr、panic 與 worker 繼承的 stderr 都進同一個檔案，寫入時與每 5 分鐘檢查，超過 8 MiB 輪替成 `.1`（被取代的 `.1` 先清空，仍在寫它的 worker 也不再占空間），被刪除會重建。每一行日誌經 `logfile::Stderr` 寫出：整行寫入或丟棄並計數，絕不 panic——tracing 寫入失敗時會再用 `eprintln!` 回報到同一個 stderr，而磁碟滿時那次列印也失敗、讓記日誌的執行緒 panic（2026-11-07 一台遠端主機的指標 writer 就是這樣死掉）。磁碟滿而寫不進時，先丟最舊的：清空 `.1`，再把目前的檔案縮到只剩最新約 64 KiB（從行首開始）（`vpn_platform::logfiles::drop_oldest`，不跟隨 symlink），然後重寫這一行；仍寫不進就丟棄並計數，下一行成功寫入前先寫「N 行日誌遺失」。受管 App 的輸出日誌在磁碟滿時也一樣先丟最舊的。
- **install**：
  - 動到任何東西之前先完成準備：把內含程式寫到暫存區，請暫存的 `vpnd build-info` 回報自己——必須能在這台機器執行、是 release、含網頁介面；服務定義先渲染並通過 `plutil -lint`／`systemd-analyze verify`。
  - 管理 port 預設 18765，被其他程式占用時自動往後找空的；`--port` 指定時必須是空的。
  - 監聽位址預設 `127.0.0.1`。`--listen-address <位址>`（例如 `0.0.0.0`）加上可重複的 `--allow-client <CIDR>`，讓列出網段裡的其他主機也能使用網頁介面與 API（§8 第 10 條）。非 loopback 位址沒有允許清單、loopback 卻帶清單、超過 32 個網段，或列出 `0.0.0.0/0`、loopback、群播、link-local 時，動到任何東西之前就拒絕（controller 啟動時也做同一個檢查）。兩者寫進 controller 的服務定義（`vpnd controller --listen-address … --allow-client …`）與安裝紀錄；預設值不寫，既有的定義維持原樣。監聽某個特定位址時 controller 另外也綁 `127.0.0.1`，本機程式與 installer 的就緒檢查照常使用它；port 必須在 127.0.0.1 與該位址都是空的。
  - 啟動後等網頁介面以新 build 回應且 manager 已連線，才算完成。
  - 全新安裝失敗時，把這次放上的服務與程式移除，資料與日誌保留。
- **upgrade**：停止服務（controller 先）→ 在服務停止時備份資料庫與服務定義（`installer/backups/`，保留最近 3 份；control 資料庫的備份不帶 SSH 下載的日誌與完成的紀錄，§7c）→ 舊程式移到 `bin.previous/` → 放上新程式與定義 → 啟動並等候就緒。過程中任何一步失敗，都會還原舊程式、定義與資料庫並重新啟動。還原前必須先確認新版本已停止（launchd 讀回 job 已卸載；systemd 讀回 `ActiveState` 為 inactive／failed）；確認不了就不動任何檔案，回報備份位置，避免舊版與新版同時執行，或舊版打開新版可能已遷移、仍在寫入的資料庫。舊版拿回的永遠是升級前停機時備份的資料庫。每次回復都會在該備份目錄寫 `rollback.txt`，內容包括時間、舊新 build、失敗原因與回復結果。備份完成前不還原任何檔案：那時還沒有改動。同一個 build、服務定義不變且服務正常時不做任何事。換 port＝`upgrade --port`；換監聽位址或允許的網段＝`upgrade --listen-address … --allow-client …`（沒有給的沿用安裝紀錄；改回 loopback 位址時允許清單一併取消）。
- **uninstall**：移除服務與程式；資料、保險庫金鑰、日誌與備份保留。`--purge` 另外刪除 VPN Manager 放在根目錄裡的東西（資料庫與保留檔、金鑰、`logs/`、`run/`、`locks/`、`apps/`、`pending-stops/`、`installer/`），刪除前先確認那是 VPN Manager 的目錄；根目錄裡其他的檔案與資料夾一律不動（`--root` 可以指向本來就有東西的目錄），只有清空之後根目錄才一起刪除（2026-11-14；之前是整個根目錄遞迴刪除）。
- **status**：服務狀態、網頁介面回應的 build 是否與安裝紀錄相符、這個 installer 內含的版本是否與已安裝的相同。開放給區網時，install、upgrade 與 status 都另外印出區網網址、允許的網段，以及「這些網段裡的任何裝置都能操作 VPN Manager（包括啟動受管 App），沒有登入」。
- 管理 port、監聽位址與允許的網段都是安裝參數，不是應用程式設定；`SystemStatus.controller_port`、`controller_listen`、`controller_allow_clients` 與 `data_dir` 回報實際值，`host_addresses` 是其他主機連得到的這台主機位址（不含 loopback、link-local）。
- `SystemStatus.observed_at` 是網頁服務送出回答的時間：網頁以它得到主機與瀏覽器的時差，伺服器的時間戳記一律以主機的時間判斷（docs/frontend-design.md「主機的時間」）。`clock_synchronized`：Linux 以 `adjtimex`（只讀，不改任何設定，不需權限）讀核心記的最大誤差，小於 16 秒算已同步，與 systemd（`timedatectl` 的 System clock synchronized）同一條規則——NTP 用戶端（systemd-timesyncd、chrony、ntpd）讓它保持很小，沒有時每秒增加 0.5 ms，到 16 秒核心就標為未同步（開機時也從這裡開始）；其他系統是 null。沒有同步時診斷多一項警告（`clock`）、`vpnctl status` 多一行（2026-11-07；一台遠端主機沒有任何 NTP、時鐘慢 30.5 秒，網頁上的即時數字全是「—」）。

## 6. Store 與秘密

- `control.sqlite`（WAL、`synchronous=FULL`）與 `metrics.sqlite`（WAL、`synchronous=NORMAL`）分開，各自單一 writer thread＋有界佇列（滿回 `STORE_BUSY`）＋讀取池。只有 `crates/store` 依賴 rusqlite。
- `metrics.sqlite`（schema 8）：每條執行中的連線每秒一筆樣本（累計計數、gauge、generation 與 worker 單調時鐘），其中每個代理埠另記一筆（`gateway_series`／`gateway_samples`）；每分鐘與每小時的 rollup（`metric_buckets`／`gateway_buckets`）。連線的 payload 是各代理埠的 payload 加上轉發 relay 的位元組與（嚴格隔離時）App 沙箱的 App 流量（§4.3；嚴格隔離時轉發就在 App 沙箱的部分裡；2026-11-07 之前的資料沒有轉發）；第 7 步在樣本加上 App 沙箱的部分（`sandbox_rx`、`sandbox_tx`），在 rollup 加上它與它涵蓋的時間（`sandbox_rx`、`sandbox_tx`、`sandbox_ms`）。沒有 sandbox 的連線與第 7 步之前的資料是 NULL：未知，不是 0；這些欄位在既有的表裡，rollup、保存期限與空間上限跟同一列的其他欄位一起處理。API 以 `sandbox_rx_bps`／`sandbox_tx_bps`（每點）與 `sandbox_rx_bytes`、`sandbox_tx_bytes`、`peak_sandbox_*`（總量）另外列出這一部分，代理埠的 scope 一律是 null；即時速率 `LiveRates.sandbox` 同理。第 8 步（2026-11-07）在連線與每個代理埠的樣本加上 SSH 的兩個部分（§7c）：SSH 代理（`ssh_rx`、`ssh_tx`）與 SSH 下載（`ssh_pull_rx`、`ssh_pull_tx`），rollup 另有它們涵蓋的時間（`ssh_ms`）；連線的值是各代理埠的和，與 payload 同一個 lineage。第 8 步之前的資料是 NULL（未知）。API：每點 `ssh_rx_bps`／`ssh_tx_bps`、`ssh_pull_rx_bps`／`ssh_pull_tx_bps`，總量 `ssh_*_bytes`、`ssh_pull_*_bytes`、各自的峰值，以及去掉兩者後的峰值 `peak_non_ssh_*`（代理埠的一般代理流量）。延遲是固定區間的直方圖（`latency-us-v1`）：連線延遲為各代理埠相加，DNS 延遲只計上游回答（快取命中不算），逾時另計、不是延遲值。代理連線失敗另記其中「名稱不存在」（NXDOMAIN 或沒有可用位址）的次數；schema 5 之前的資料沒有這個數，是未知而不是 0。查詢（`GET /v1/metrics/series`）在 manager 計算：只用同一 generation 內的計數差；分位數＝合併區間後第一個累計數 ≥ ceil(q×count) 的區間上界（`bucket_upper_bound`），落在 +∞ 區間或沒有樣本時是 `null`，不平均每秒的 p95；`scope=all` 只加總已知值並附每點 `reporting`。保存：原始樣本依設定（小時）、每分鐘 30 天、每小時 180 天；超過空間上限時從最舊的資料先刪，並記成 `quota` 缺口；收集器丟棄的樣本記成 `dropped` 缺口。每份回答都附缺口與原因、重新啟動的位置，以及有上限的清單（`METRICS_MAX_LISTED`、`METRICS_MAX_GAPS`），保證放得進一個控制訊框。
- 效能（Performance Manager，只有被動觀測）：`metrics.sqlite` 第 4 步是程序資源（`resource_series`／`resource_samples`／`resource_buckets`／`resource_gaps`：manager、controller、各 worker；每 5 秒、以「pid＋啟動時間」（worker 再加 generation）辨識程序；原始 24 小時、每分鐘 30 天，與指標共用空間上限）。主動測試移除後（§9），metrics 第 6 步刪除 `performance_reports`、`benchmark_measurements` 與 runner／測試對端的程序樣本；control 第 6 步（`performance_runs`）照原樣保留在遷移步驟中，第 10 步把它與 kind `performance_target` 的實體刪除。
- 設定實體為**不可變 revision**；更新產生新 revision，執行中的 worker 繼續用啟動時固定的 revision。
- control schema 目前是第 14 步。第 14 步（SQL）把 `udp_direct: false` 寫進每一個在它之前存的轉發 revision（與第 12 步相同的做法：`json_set`、只補沒有這個欄位的、不新增 revision、其餘內容不變）：較舊的程式有了這一步就拒絕這個資料庫，不會讀進來後把使用者要直接送進沙箱的 UDP 改回保留 port 並轉送。第 13 步是 SSH 下載（見下方）。第 12 步（SQL）把 `proxy_protocol: false` 寫進每一個在它之前存的轉發 revision（`json_set`，只補沒有這個欄位的、不新增 revision、其餘內容不變）：舊版程式不認得這個設定，有了這一步它會拒絕這個資料庫，而不是讀進來後不送標頭就轉送。第 11 步（程式步驟）建立 `builtin_blocklists`（每個內建清單建立的實體，或使用者刪除它的時間：刪除的不會自動加回，`POST /v1/blocklists/builtin/{key}/restore` 復原；同網址的使用者清單直接成為內建清單），把內建清單加入每個既有安全設定一次、打開自動封鎖（修訂歷史顯示曾開啟後被關閉的除外），做了什麼寫進事件記錄 `store.migration`；每次啟動依目錄同步（後來加入的清單會建立，網址改了的內建清單跟著改）。第 9 步是 `bootstrap_journal`（§7）；第 10 步刪除已移除功能的紀錄：主動測試的 run 與測試對端、舊資料匯入的 `legacy_imports`／`legacy_import_items`（第 3 步建立），以及只有還原才會留下的 App 意圖（沒有對應的 App、也沒有執行中的 run）；匯入建立的設定與秘密是一般資料，保留。歷史步驟維持原樣，舊資料庫仍一步步遷移。Store 的備份／驗證／還原已移除（§9）；資料目錄裡舊版留下的 `backups/`、`restore/` 等不再讀取、列出或刪除。installer 升級時的資料庫備份與失敗回復是另一回事，仍在（§5.5）。
- **磁碟空間**（`crates/store/src/disk.rs`，以 statvfs 讀取，探測可替換以便測試）：指標永遠不停止記錄，磁碟滿時覆蓋最舊的資料（環狀緩衝）。剩餘空間低於 min(512 MiB, 5 %)，或指標寫入遇到 `SQLITE_FULL` 時，指標資料庫不再變大：每次寫入前若檔案裡的空頁少於 128 頁，就從最舊的資料刪起（已彙總的原始樣本、每分鐘、每小時 rollup，最後是程序樣本；空間上限也不刪的最新資料一樣不刪）直到有 512 頁空頁，每次刪除記為該層的 `disk_low` 缺口；空頁留在檔案裡給新的列重用，不還給磁碟，所以寫入與 checkpoint 都不需要新的磁碟空間。WAL 有界且保留自己的區塊（`wal_autocheckpoint` 256 頁、`journal_size_limit` 4 MiB），checkpoint 後下一次寫入從頭覆寫；暫存表在記憶體（`temp_store=MEMORY`）。指標寫入仍遇到 `SQLITE_FULL` 時：釋放 8 MiB 的 `metrics.reserve`、`wal_checkpoint(RESTART)`、再騰出空頁，然後重試一次；連這樣都放不下才放棄這批樣本，記為 `disk_low` 缺口（collector 視為已處理，佇列不會變大或重試）。啟動時磁碟已幾乎滿（剩不到 8 MiB）就先釋放 `metrics.reserve`，讓兩個資料庫的 WAL 與共享記憶體檔有空間開啟。空間回到門檻以上 25 % 後資料庫可以再變大，兩份保留空間依序重新配置。空間上限（設定 `metrics_quota_mib`，預設 512 MiB）仍是使用量的上限。資料目錄中預先配置 8 MiB 的 `control.reserve`：控制資料寫入遇到 `SQLITE_FULL` 時釋放保留空間並重試一次；每個控制寫入都是單一敘述或單一交易，所以重試重做的是完整回滾的單位（不會只剩一半，或重複一筆事件）；控制資料與秘密永遠不刪。一個工作不會拖垮整個資料庫：writer 與讀取池在 job panic 或留下未結束的交易時 rollback（什麼都不寫入），只讓那個 job 失敗（`StoreError::Aborted`），下一個 job 照常；collector、rollup／清理與程序取樣的迴圈遇到任何錯誤（包括 `Closed`）都只是記下並重試，不會結束。`GET /v1/system/status` 的 `store.metrics_recording`（`recording`／`overwriting`／`failing`，從何時、可用空間與恢復變大的門檻、已覆蓋的列數與沒能保存的樣本數、失敗原因）說明現在的記錄；`metrics_ok` 只在寫入失敗時為 false。數據統計在覆蓋過最舊的資料或寫入失敗時於工具列下方提示（「磁碟已滿，已覆蓋最舊的紀錄」），總覽的「需要處理」列出它，`vpnctl status` 印一行。系統頁的診斷報告有 `disk_space` 檢查（兩份保留空間與覆蓋的資料）。
- 轉發（control schema 第 7 步）：`forward_evidence` 每個轉發每個協定一列，記最近一次外部連入的時間與當時的連線、tunnel port（轉發改了連線或 tunnel port 就不再算數）；隨轉發刪除。轉發本身是 revision 實體（kind `forward_binding`），被引用的 App 與連線不能刪除。
- SSH 下載（control schema 第 13 步，`crates/store/src/ssh_download.rs`，§7c）：工作是 revision 實體（kind `ssh_download_job`；被引用的代理埠不能刪除）；`ssh_download_state` 每個工作一列（暫停、記下的主機金鑰、等待確認的新金鑰）；`ssh_download_transfers` 每個檔案一列（`claiming`／`downloading`／`finalizing`／`local_done`／`failing` 未結束，`completed`／`failed` 有結束時間，由 CHECK 保證；結束的只留最近 1000 筆，工作設了保留天數時更早的也刪除）；`ssh_download_log` 每個工作最多 500 筆。刪除工作時三個表的列、秘密與本機部分檔一起刪除。control 資料庫刪除的內容不留在空閒頁與 WAL（`secure_delete`、清除後截斷 WAL、這版第一次啟動時 `VACUUM` 一次；`crates/store/src/scrub.rs`，§7c）。
- 安全（control schema 第 4 步）：IP 封鎖清單是 revision 實體（kind `blocklist`，被安全設定引用時不能刪除），合併後的範圍存在 `blocklist_content`（清單 id＋revision，只留最新）；`blocklist_refresh` 是網址清單最近一次更新的結果與 stale 起點；`bans` 是自動封鎖（`UNIQUE(instance_id, source)`、到期時間有索引）；meta `policy_revision` 是 overlay 版本的全域單調計數（與 generation 相同）；到期的自動封鎖由下一次清理刪除。
- 秘密：XChaCha20-Poly1305，每筆獨立隨機 nonce，AAD 綁 `installation_id|secret_id|kind|key_id`。沒有任何讀回明文的 API。寫在磁碟上的格式由一組固定向量守著（`vault.rs` 的 `what_the_earlier_crates_wrote_still_holds`，2026-11-11 換到新一代的加密 crate 時加入）：先前的 crate 封存的秘密要能打開，金鑰檢查值與請求指紋要是同樣的字串；換加密 crate 時這個測試不過就不能升。
- 32-byte master key 由 VPN Manager 自己保管：根目錄裡的 `vault.key`（0600，目錄 0700，O_NOFOLLOW），不交給 Keychain、Secret Service 或 systemd credential 等外部元件。金鑰和它保護的資料放在一起，一起備份、搬移與刪除；能讀這個使用者檔案的人就能讀到金鑰（靜態保護由 FileVault／LUKS 提供）。
- 金鑰配對檢查：資料庫記錄主金鑰的 HMAC 指紋（`vault_key_check`）。金鑰被換掉或遺失時，manager 拒絕啟動並說明原因，不會默默產生新金鑰、讓既有秘密再也打不開。沒有這筆紀錄的舊資料庫，以既有的一筆秘密驗證後補記。
- 明文只出現在：`POST /v1/secrets` 的短暫 ingress、manager 的 Store、交付給 worker 的私有 channel、Provider 工作期間的短暫租約（用完 zeroize）。

## 7. Provider 出口

- 全域只有一個 Provider egress binding：所有 Provider API 呼叫都經「使用者選定的 Instance」的私有 connector 送出（TLS 在 controller 端終結，worker 只看到 TLS bytes）。
- **controller 程式裡沒有任何 host dial 與 host DNS**（`crates/controller/tests/no_dial.rs` 掃描 controller 與 adapter 原始碼確保）。它只連得到 manager 的兩種中繼 socket：選定出口 Instance 的 connector（流量在其 tunnel 內），或 bootstrap 授權期間的直連中繼。兩者使用同一行請求協定（relay line v2，定義在 `vpn_ipc::relay`）：`{"v":2,"host","port","family","nonce","route":{"mode":"instance","instance_id","generation"}|{"mode":"bootstrap"},"expect"?:{"connector","network"}}`。回應帶目前的 epochs；connector 以 `NONCE_REUSED`、`WRONG_ROUTE`、`EPOCH_CHANGED`、`BAD_VERSION` 拒絕，v1 一律拒絕（controller、manager、worker 是同一個 `vpnd` build）。controller 只有一條連線路徑。
- **首次 bootstrap**：在 `bootstrap_consumed` 尚未寫入、出口未停用、也還沒有選定出口連線時，可由使用者明確允許一次限時（10 分鐘）的原網路例外。由 manager 解析並連線（只限 `BOOTSTRAP_ALLOWLIST` 的固定 `(host, port)`，只走要求的 IP 版本，解析結果是私網或特殊位址一律不連），並轉送位元組；grant 到期、撤銷、選定出口或 `bootstrap_consumed` 寫入時，manager 取消所有轉送——即使 controller 有 bug 想重用舊連線也不可能。第一條由 Provider 建立的連線就緒後自動設為出口，經新路徑檢查出口成功才永久鎖上 `bootstrap_consumed`（資料庫 trigger 保證只進不退）；之後重開機、故障都不會再直連。若使用者已手動匯入 Profile，直接選它當出口，不需要 bootstrap。
- **直連例外的日誌**（control schema 第 9 步 `bootstrap_journal`，`crates/store/src/bootstrap.rs`）：每次直連例外（首次設定與每次手動重新直連）一列。由 SQLite 強制：首次設定只有一列、永久保留，鍵是 `sha256(installation_id + "/initial-bootstrap-v1")`，任何一列都不刪除、不換鍵；同時最多一個進行中的 run（partial unique index）；latch 寫入後首次設定再也拿不到 grant；重新直連的列只能在 latch 已寫入時存在；封存意圖不能撤回，封存過的 run 永遠封存。
- **一個 run 一條連線**：run 在送出任何 Provider 請求前先認領它唯一的連線，之後在同一筆交易內建立連線並把意圖設為 running（不需要另外 Start）。第二個請求會被拒絕（`BOOTSTRAP_IN_PROGRESS`），重試會拿回同一條連線。認領（reservation）從取得或最後一次續約起 90 秒失效；仍在建立中的請求每 20 秒續約一次（`BootstrapRenewChild`，只續還由同一個請求持有、尚未建出任何東西的認領）。所以 controller 在建立中途當機，最多擋住其他請求 90 秒，而不是整個 10 分鐘的 grant；慢的建立（AirVPN 一次最多試 4 個位址、Mullvad 建立裝置）不會被第二個請求搶走而多建一個裝置。
- **封存**：分三步，每一步落盤後才做下一步：寫入封存意圖 → 關閉 grant → 提交 latch 與出口綁定。controller 的背景工作（`crates/controller/src/egress.rs`）負責完成升格，因為出口檢查需要 controller 的 TLS client；manager 保存耐久紀錄並執行封存。Store 拒絕封存的提交（寫入佇列滿、磁碟滿、I/O 錯誤）時，controller 的升格工作會重送封存（1 秒起倍增到 30 秒），直到成功，不必等下一次 manager 啟動；過程中直連一直維持關閉。只有 Store 確認連線已不存在，升格才把它記為已刪除（`CHILD_GONE`）；manager 回答「找不到」本身算未知，run 等到期限為止。啟動時，manager 結束逾期的升格，並把中斷的封存往前完成（latch 寫入、選定新連線），出口在那條連線 Ready 前維持封鎖或啟動中，**永遠不會重新開放直連**。
- **直連 grant 的範圍**：只服務建立出口的操作（登入、帳號、裝置、伺服器清單、建立連線），而且每個請求仍要先通過 guard 的新出口檢查；撤銷裝置、下載封鎖清單之類的操作經直連一律拒絕。首次設定與手動重新直連都套用同一範圍。
- **手動重新直連**（`POST /v1/provider-egress/rebootstrap`，需要 If-Match、Idempotency-Key 與 `{"confirm_direct": true}`；`DELETE` 同一路徑取消；`vpnctl provider-egress rebootstrap --confirm-direct｜--cancel`）：只有出口處於 `recovery_required` 時才允許，也就是金鑰不見了（`KEY_MISSING`），或伺服器連續 3 次不回應握手（`unreachable_attempts`）。有其他設定或連線能用、出口是使用者手動停止的（急停時原因寫明要先解除急停）、tunnel 正常但檢查失敗、或有未確認的停止時，都不允許（未確認的停止回 `EGRESS_NEEDS_DECISION`，附連線的原因），回 409 `REBOOTSTRAP_NOT_ELIGIBLE` 並附原因。允許時開一個 10 分鐘的 grant，走 v2 bootstrap 中繼；取消、到期與當機都會撤銷 grant；latch 一直維持 true。出口狀態多了 `recovery_required` 階段、`bootstrap`（目前或最近一次 run）與 `recovery`（是否允許與原因）。已知缺口：controller 在建立 Mullvad 裝置之後、建立連線之前當機，那個裝置與金鑰會留著，沒有依金鑰對帳；下次嘗試時介面的預設會再選它。
- 原設計是以 SCM_RIGHTS 把直連 socket 交給 controller、manager 保留 dup 再 `shutdown()`；改為 manager 端中繼，保證相同（manager 隨時能切斷），但 controller 不必處理 FD 轉交，也與 Instance connector 共用同一協定。
- **每次實際 HTTP 前做 IP preflight**（同 connector、同 address family），結果綁一次性 permit；面板分開顯示「路徑是否經 tunnel」與「出口是否屬於該 Provider（match／other／unknown）」。unknown 不畫綠色。每個 Provider 操作有一個 guard（`crates/controller/src/provider/guard.rs`），釘在操作開始時的出口路徑上；token、帳號、裝置、建立與其對帳、每一次 AirVPN bootstrap 嘗試、伺服器狀態與清單都經過它。每個請求依序：
  1. 在該 origin 的預算中同時預留出口檢查與請求本身；
  2. 向 manager 讀出口路徑，與操作開始時不同（切換、重建、停用）就拒絕，不跟著新路徑走；
  3. 經同一路徑、同一 IP 版本做一次新的、不帶任何憑證的出口檢查；
  4. 寫出 relay line 前，路徑必須不變、檢查必須在 2 秒內（`PERMIT_TTL`）；檢查過期就重做一次，再過期就拒絕，過期的檢查永遠不用；
  5. relay line 帶一次性 nonce、路徑與檢查時看到的 connector epoch 與 network epoch；
  6. TLS 完成、送出第一個 HTTP byte 之前，再讀一次路徑，並比對 method、host、path 的摘要與準備時一致（這一步不檢查年齡，慢的 tunnel 不會在 TLS 期間失敗）。
- **epoch**：出口 epoch 沿用 `ProviderEgress.route_revision`（切換、停用、bootstrap 用盡都會前進），重建以 generation 區分；network epoch 是 worker 內每代一個的計數，payload gate 每次重新開啟（睡眠、網路變更、對端沉默後）就前進，connector 撥號後再檢查一次，bootstrap 中繼固定為 0；connector epoch 是每個 connector 或每個 grant 隨機產生。
- **預算**（`budget.rs`）：屬於 origin（`api.mullvad.net`、`airvpn.org`、AirVPN bootstrap 位址），不屬於路徑，切換出口不會重置。每個 origin 可連續 20 個、每秒回補 1 個，最多排隊 5 秒，超過就立即拒絕並告知要等多久；429 依 `Retry-After` 暫停該 origin（沒給時 30 秒，上限 1 小時），暫停期間什麼都不送。App 與代理埠的流量在 worker 內轉送，永遠不經過這個預算。
- **AirVPN 功能檢查**：出口檢查、會員歸屬、IPv6、設定產生、連入埠保留分別記錄（passed／failed／blocked／not_applicable／unverified）。連入埠保留在經網站讀取或操作前是 unverified；操作成功為 passed，網站要求驗證碼或兩步驟驗證為 blocked，登入失敗（帳密被拒、多次失敗暫停）或網站格式不符為 failed；其他失敗（連線、預算、出口、網站拒絕單一操作）不改變它。IPv6 在明確按「檢查出口」時單獨檢查，IPv4 通過不代表 IPv6；IPLeak 的觀測通過不會讓其他項目變成通過。顯示在出口狀態列的「功能檢查」、帳號頁的「AirVPN 功能檢查」與 `vpnctl provider-egress inspect`。`/v1/provider-egress/check` 與 `/v1/instances/{id}/ip-check` 也走預算並記錄這些項目；連線的檢查不會覆寫出口的最近一次檢查。
- **AirVPN 連入埠（經網站，2026-11-02）**：AirVPN 的 API 沒有連入埠服務，網站 Client Area 的 Ports 頁以 XHR 表單操作（`POST /ports/`：`action`、該動作的欄位、`ecsrf`、`render=ajax`；JSON 物件含 `error` 即為失敗）。VPN Manager 以帳號自己的帳密（每個操作從 vault 租用一次）登入網站，代為送出頁面上除了 `graph` 之外的所有操作（`crates/providers/src/airvpn/site/`）：`manifest`（列出）、`insert`（保留，指定或由 AirVPN 挑選）、`delete`；每項設定一個請求（`edit_note`／`edit_enabled`／`edit_device`／`edit_protocol`／`edit_layer`／`edit_localport`／`edit_ddns`，帶 `port`、`pool`、`value`）；先 `sessions` 再對每個 TCP 項目 `test`（UDP 不測，與網站相同）；`ddns_report`；`seq_search`（只查詢連續的空閒埠，不保留）。每個請求都經 Provider 出口 guard（新的出口檢查、一次性 permit、airvpn.org 預算），工作階段只在記憶體、每個帳號一次一個網站操作。修改先依頁面規則檢查（備註一行 ≤200、裝置 `all` 或帳號的金鑰、local port 1–65535、DDNS 名稱字母數字連字號 ≤60），只送出和最新清單不同的項目，之後重新讀取：讀回的值才算儲存；被拒絕、讀回不同或沒送出的項目回 `PROVIDER_REJECTED`（逐欄 `NOT_SAVED` 與 AirVPN 的原因），讀不回來是 `OUTCOME_UNKNOWN`（不重送）。測試只有 AirVPN 的 `ok` 算連得進來、`error` 是連不進來、`warning` 是警告，其他字詞一律「結果不明」並附 AirVPN 的說明；每項最多 15 秒，35 秒後不再開始新的測試；沒有連線使用這個埠時回空清單。API：`GET`／`POST /v1/provider-accounts/{id}/forwarded-ports`、`PATCH`／`DELETE …/forwarded-ports/{port}`、`POST …/{port}/test`、`GET …/forwarded-ports/ddns`、`GET …/forwarded-ports/free?count=2–10`；變更需要 Idempotency-Key（測試不改變任何東西，不需要），沒有本機 revision 所以不需 If-Match；`vpnctl provider ports list｜reserve｜delete｜edit｜test｜ddns｜free`；網頁在帳號頁的「連入埠」與轉發對話框。DDNS 名稱在 API 裡一律是 `.airdns.org` 之前的部分。轉發需要 local port 等於公開 port：清單在被改掉時提示，設定對話框與 `vpnctl provider ports edit` 在不同時警告；轉發本身不因連入埠的設定而改變。
  - 每個網站請求都是該操作 guard 的一個請求：新的出口檢查、`airvpn.org` 的預算、relay line v2，只用 IPv4；只在 VPN 出口上進行，直連 grant 一律不帶（它不是建立出口的操作）。
  - 網站 session（cookie 與 Ports 頁的 token）只在 controller 的記憶體、只送往 airvpn.org，不寫入任何地方、不顯示；同一個帳號同時只有一個網站操作，session 在操作之間重用，帳號移除時丟棄並清零。回應顯示已登出時，一個操作最多重新登入一次。登入時勾「匿名登入」、不勾「記住我」。
  - 帳密被拒、多次失敗暫停、驗證碼、兩步驟驗證與表單改變分開回報（`PROVIDER_AUTH_REJECTED`、`PROVIDER_QUOTA_EXCEEDED`、`PROVIDER_LOGIN_CHALLENGE`、`PROVIDER_CONTRACT_DRIFT`），不自動重試；登入頁的表單不認得或已經要求驗證碼時不送出密碼。保留或刪除沒有得到已知的成功回應時，以新讀取的清單判定結果，從不重送，仍判定不了就回 `OUTCOME_UNKNOWN`。形狀不符的回應是 contract drift，只在 debug 記錄狀態與去除帳密、cookie、token 的片段。
  - 網站的規則（2026-11-02 讀取）：每個帳號最多 5 個（`PORT_LIMIT_REACHED`）、port ≥ 2049、所有伺服器相同、premium 方案到期 10 天後釋出；P2P 程式必須在轉發的同一個 port 監聽，網站上的 local port 被改成別的時畫面會警告。port 範圍在記錄操作、連絡 AirVPN 之前就檢查；上限與是否已保留，以保留前新讀取的清單檢查。Mullvad 與一般設定回 `UNSUPPORTED_CAPABILITY`（`forward_reservation` 只支援 AirVPN）。
- **入口與出口（2026-11-08）**：由 Provider 建立的連線可以分開選入口與出口（`crates/controller/src/provider/route.rs`）。`ProviderConnectInput` 與 `ProviderServerChangeInput` 的 `server_id` 一律是出口，選填的 `entry`（`ProviderEntryInput`）是入口；不帶 `entry` 就是出口伺服器的預設入口，與加入這個功能前相同。入口依 Provider 能做的檢查，不能用的回欄位錯誤（`/server_id`、`/entry`、`/entry/server_id`、`/endpoint_family`），不猜。
  - **Mullvad（多跳）**：入口是另一台 relay（`{"kind":"relay","server_id"}`），入口與出口都必須在目錄裡而且啟用；入口等於出口就是直連。tunnel 連到入口 relay 的 IPv4、出口 relay 的 `multihop_port`，peer 用出口的公鑰（Mullvad 路由器說明的做法），只有 IPv4。`multihop_port` 只在 `https://api.mullvad.net/www/relays/wireguard/` 裡（`public/relays/wireguard/v2/` 與 `app/v1/relays` 沒有）：這份清單經 Provider 出口讀取、與目錄一樣快取 15 分鐘（`CATALOG_TTL`），伺服器清單也讀它來標示每台能不能當多跳出口（讀不到只記警告，清單照常列出）。一個 port 只有在這份清單把它對到目錄裡同一個公鑰與 IPv4、而且沒有其他 relay 用同一個 port 時才用（`MultihopPorts::port_of`）。代價：入口那一端的觀察者可以從 port 看出出口是哪一台。
  - **AirVPN**：沒有多跳，入口與出口永遠是同一台伺服器。入口是這台伺服器的一個入口位址加一個 UDP port（`{"kind":"address","index","port"}`；`index` 從 0 起算，AirVPN 的 Entry IP 1 是 0，介面顯示「位址 1」）。可選的是帳號 manifest 的 WireGuard UDP 模式（port 與 entry_index；第一個是預設，選預設等於不帶 `entry`），位址還要經 TLS 驗證的狀態清單（`airvpn.org/api/status/` 的 `ip_v4_in1..4`）確認過。
  - **一般設定**：沒有 Provider 流程，入口就是匯入的 WireGuard 設定檔的 endpoint。
  - 選擇記在 `ProfileSource::Provider.entry`（`ProfileEntry`：`relay` 帶入口的 server_id、國家與城市，`address` 帶 index 與 port），`ProfileSummary.entry` 也帶出；它只用於顯示與預選，實際連線的仍是 profile 的 peer。舊的 profile 沒有這個欄位（讀成沒有入口），寫回時也不會多出來。伺服器清單的 `ProviderServer` 多了 `multihop_port`、`entries`（AirVPN 這台伺服器可選的入口，預設在前）與 `exit_ips`（AirVPN manifest 的出口位址）。
  - 換入口或出口和換伺服器一樣：裝置與金鑰不變、只改寫 profile，使用中的連線重新啟動後才改走新的路。Mullvad 連線的出口檢查會帶回 Mullvad 回報的出口 relay（`mullvad_exit_ip_hostname` → `ProviderIpCheck.exit_server`），介面拿它和 profile 的出口比對。
- 只有人工可以切換／停用出口；出口 Instance 斷線時 Provider 工作封鎖並等同一 Instance 恢復，不會自動換線。

## 7b. SSH Manager

頂層元件：在同一個工作台管理 SSH 主機，並可讓指定主機經某個 Instance 的 Gateway 走 VPN。檔案所有權的檢查與注入防護沿用這個專案前一版驗證過的做法，改良處如下。

- **真相在 Store**：主機項目（`SshHost` 實體）存 Store；`~/.ssh/vpn-manager.conf`（0600）只是由它產生的投影。寫入前比對上次寫出內容的 SHA-256，檔案被手動改過就停用覆寫並提示，絕不靜默抹掉使用者的修改。
- **`~/.ssh/config` 只改一次**：使用者按「加入 Include」時先完整備份（0600），再在最前面加入 `Include ~/.ssh/vpn-manager.conf`；其他時候只讀（解析既有主機供 overlay 與別名衝突檢查，不展開 `Match`／其他 `Include`）。
- **兩種項目**：`host`（VPN Manager 定義的新主機）與 `overlay`（讓既有主機經 Gateway，只寫 ProxyCommand 與 ServerAliveInterval）。overlay 依賴 Include 在最前面——Include 消失時會**直連（fail-open）**，UI 以危險等級標示並提供「複製成新主機」（不可解析的新別名，Include 消失時會失敗而不是直連）。
- **ProxyCommand 用自己的 `vpnctl ssh-proxy --gateway 127.0.0.1:<port> %h %p`**：Rust SOCKS5 client，以網域名稱交給 Gateway 在 tunnel 內解析；Gateway 拒絕時印出中文原因並以非零結束，SSH 失敗而不會直連。路徑寫入穩定的安裝位置（升級不失效）。
- **嚴格白名單**：別名、HostName、User、Port、IdentityFile、IdentitiesOnly、ServerAliveInterval 等少數欄位，各有格式限制；換行、`=`、引號、`%` 與任意 ssh 指令不可能寫入。私有／loopback／CGNAT 位址與 `.local` 不能經 VPN。經 VPN 時 ServerAliveInterval 必填且小於 Gateway 閒置上限。
- **寫檔是 Platform 操作**：由 manager 以 `O_EXCL|O_NOFOLLOW` 暫存檔、完整寫入、fsync、rename、目錄 fsync 原子寫入；拒絕 symlink、非本 UID、可被他人寫入的目標。controller 只做驗證與 API。
- **連線測試**：經 Gateway 對目標做 SOCKS5 CONNECT 並讀取 SSH banner（不認證），證明該路徑可用；直連主機不提供測試（使用者自行 ssh 即可）。
- **實作（2026-10-26）**：`crates/ssh`（ssh_config 唯讀解析、投影產生、檔案操作、SOCKS5 client）、`crates/vpnctl`（`ssh-proxy`）、manager 的 `SshProjector`（主機或 Gateway 變更後重新產生；寫過內容的 SHA-256 存在 manager 私有狀態目錄，用來分辨「VPN Manager 寫的」與「被手動改過」）。調整：私有位址經 VPN 改為**警告**而非錯誤——安全設定允許該網段時（辦公室、實驗室）可以到達，不允許時 Gateway 明確拒絕、不會直連；loopback、link-local、`localhost`、`.local` 仍是錯誤。沒有任何 SSH 主機時不建立 `vpn-manager.conf`（不在使用者的 `~/.ssh` 留下沒要求的檔案）。Gateway 被 SSH 主機使用時不能刪除（IN_USE），改埠會立即重新產生 ProxyCommand。驗證：真實 OpenSSH `ssh -G` 解析產生的設定、`ssh -v` 經 vpnctl 與 tunnel 取得實驗室伺服器的識別字串。

## 7c. SSH 下載

2026-11-06 新增：指定遠端資料夾與本機資料夾，新檔案自動下載，在網頁看進度、紀錄與日誌；**整個機制只經 VPN，沒有 VPN 就不能用**。做成獨立的內部元件。

- **元件邊界**：`crates/ssh-download`（`vpn-ssh-download`）在 manager 程序內執行，只經四個窄介面接觸其他部分：Store（自己的實體與三個表，§6）、vault（密碼與金鑰密碼）、`Routes`（代理埠查詢：`Route::{Ready, Waiting, Invalid}`，以及「連線狀態變了」的通知）、`Publish`（狀態事件）。manager 側的轉接只有 `crates/instance-manager/src/downloads.rs`；controller 只驗證欄位與轉送（`/v1/ssh-downloads*`、SSE `ssh_download_status`，每個工作每秒最多一次），檔案內容不經 controller（第 2 條）。
- **只經 VPN（fail closed）**：元件唯一會開的連線，是到自己代理埠（loopback）的 SOCKS5，附安裝金鑰證明（私有方法 0x80，§7b），伺服器名稱原樣交給代理埠在 tunnel 內解析；元件裡沒有主機 DNS 或任何直連（`tests/no_direct.rs` 掃描原始碼）。只有代理埠所屬的連線 Ready、沒有急停、代理埠正在服務時才有路由；其他情況（連線停止或未就緒、代理埠停用或不在服務、狀態未知）工作顯示「等待 VPN」與原因，2 秒起倍增到 60 秒再試，連線階段或代理埠狀態一改變就立刻再試；代理埠拒絕（0x02）同樣是等待。代理埠接下連線時等待才結束，之後顯示「連線中」。只有 HTTP 的代理埠或不存在的代理埠，儲存時就被拒絕。
- **流程**（移植 `workflow.rs`；每一步先記錄再動手，`ssh_download_transfers`）：列出來源資料夾（只取一般檔案；檔名篩選三種：全部、略過含 UUID（原工具的 `IS_FILTER_UUID_FILE`）、只要含 UUID；預設略過 `.` 開頭）→ 記為 claiming 後把遠端檔案改名到處理中資料夾的 `<transfer-id>`（已被拿走就放棄這筆）→ 下載到本機資料夾的 `.vpn-manager-partial/<transfer-id>`（中斷後從部分檔的長度續傳；同時送出的讀取請求數隨路徑調整，見下方「讀取管線」；60 秒沒有進度算中斷）→ 先記下最終檔名，再以硬連結把部分檔放到那個名稱（已存在的名稱不會被取代；沒有硬連結的檔案系統改用不覆蓋的 rename：Linux `renameat2(RENAME_NOREPLACE)`、macOS `renameatx_np(RENAME_EXCL)`），同名時改成 `名稱--<傳輸紀錄的 id>.副檔名`（副檔名不變；2026-11-10 實機確認，之前這裡寫的 `名稱 (2)` 與程式不符），fsync → 記為 local_done 之後才移除部分檔的名稱並刪除遠端的處理中檔案 → completed。連續幾次（預設 3）沒有進度的檔案移到失敗資料夾（同名加編號），記為 failed。manager 重新啟動或連線中斷後從紀錄接著做：不遺失、不重複，遠端檔案只在本機檔案完整放好之後才刪除。處理中與失敗資料夾預設是來源資料夾旁的 `doing`、`failed`。
- **來源與成品的身分**（2026-11-11，`transfer.rs` 的 `resume_point`、`RemoteStat`，`local.rs` 的 `place`／`is_placed`）：續傳之前，把部分檔頭尾各 64 KiB 和遠端同一位置的內容比對，不同就清空部分檔從頭下載（日誌 `SOURCE_CHANGED`）——來源在兩次嘗試之間被換成同樣長度或更長的另一個檔案時，不會接成兩個版本的混合。一次嘗試的前後各讀一次大小與修改時間（handle 沒有大小時改讀路徑），大小不同、或伺服器兩次都有回報而修改時間不同，這次嘗試就不算完成。這仍然不是內容摘要：只改動中段、長度與修改時間都不變的來源偵測不到，要完整的保證得由來源端提供摘要。當機後的成品認定只看檔案本身：硬連結之後部分檔和成品是同一個 inode，名稱已存在時以 `(st_dev, st_ino)` 相同認定那是這次下載放的；部分檔不在時，同名同大小的檔案不算，重新下載後另存成帶編號的名稱，遠端在那之後才刪除。
- **讀取管線**（2026-11-10，`crates/ssh-download/src/pipeline.rs` 的 `Pipeline`）：伺服器在請求送出一個往返之後才回答，所以一個檔案每個往返最多前進「在途請求數 × 128 KiB」。原本固定 16 個（在途 2 MiB），往返 307 毫秒時一個檔案只有 3.2 MB/s，同一條路徑四個檔案同時卻有 21–22 MB/s。現在從 16 個開始，每 2 秒（至少 8 個回答）看一次：一個讀取從送出到回答的時間少於最短那次的 3 倍就加倍（最多 128 個，在途 16 MiB），到 8 倍就減半，中間不動。讀取花的時間就是排隊的量（在途的量 ÷ 速率），不需要另外量往返時間；門檻是「幾個往返」而不是一個，因為 sshd 傳檔時沒有關 Nagle，佇列一空，每個回答的最後一段要等前面的資料被確認才送出，等於每個讀取多一個往返（深度 16 時讀取時間是最短的 2.1 倍，深度加倍後速度變三倍）。SSH channel window 從 4 MiB 改成 32 MiB，不會成為限制。每次調整寫一行 debug 日誌（只有數字）。實測同一條路徑一個檔案穩定在 11.9 MB/s，深度停在 64（讀取 705 毫秒，最短 313 毫秒）。
- **在途讀取的總量**（2026-11-11，`pipeline.rs` 的 `ReadBudget`）：所有正在下載的檔案合計最多有 128 MiB 的讀取在途（`Options::read_budget`，等於一個工作 8 條連線都到最深的管線）。每條正在讀取的連線平分這個量，但不少於起始的 16 個讀取（2 MiB）：剛開始的檔案不會被旁邊的大檔案拖慢，大檔案的管線隨著回答收到而讓出。之前每條連線可以各自到最深，24 條連線就是 384 MiB，本機磁碟一慢就變成這麼多記憶體。8 個檔案以內不受影響；更多時，合計速率的上限是「128 MiB ÷ 一個讀取花的時間」。量測（release 建置，在測試用的 SSH 伺服器前加一段只增加延遲的轉送，往返 600 毫秒，24 個 160 MiB 的檔案，各三輪）：在途從 336 MiB 降到 126 MiB，測試程序的記憶體峰值從 509–533 MiB 降到 261–265 MiB，合計速率從 226 降到 151 MiB/s（這條測試路徑沒有頻寬上限，速率完全由在途的量決定）；8 個與 4 個檔案時三項都不變。
- **一個大檔案用多條連線**（2026-11-11，`pipeline.rs` 的 `Reads`／`Lane`，`transfer.rs` 的 `Assist`）：一個檔案的讀取分成兩邊。傳輸依檔案的順序提出讀取，也照這個順序把回答寫到檔案尾端；每條服務它的連線是一條通道（lane），有空位就拿下一個讀取，各有自己的管線深度與預算份額。傳輸同時提出的讀取數就是各通道空位的總和，所以「已提出、還沒寫入」的量仍然在預算之內。還剩至少 64 MiB（`Options::large_file`）的檔案會開放給同一個工作裡沒有別的事可做的連線（必要時為此登入）：它們在自己的連線上開同一個遠端檔案，回答傳輸提出的讀取。本機檔案仍然只有一個寫入者、只往尾端寫，所以續傳、當機後的認定與紀錄都不變，沒有新的磁碟格式；每個回答寫入前都確認它的位置就是檔案目前的尾端、長度不超過要求的。協助的連線先確認自己開到的是同一個檔案才服務——大小與修改時間和傳輸的 handle 回報的相同、頭尾各 64 KiB 的內容和傳輸讀到的相同；不同表示路徑下的檔案被換過，這次嘗試不算完成（日誌 `ATTEMPT_FAILED`「另一條連線在同一個路徑讀到不同的檔案」），下一次從比對已下載的部分開始。協助的連線中斷，或有讀取在途卻 30 秒（停滯逾時的一半）沒有回答時，只是它離開：它拿走的讀取排到最前面由其他連線重讀，檔案的這次嘗試不受影響；一個檔案連續 3 次協助不成之後不再找協助。協助只用沒有人要的連線：整個 manager 的 24 條連線只剩一條空著時，沒有連線的 worker 不會為了協助而登入；全部用完時，一條只在協助的連線把在途的讀取回答完就關閉、還回去（一次一條，不夠再下一條），所以別的工作自己的檔案不必等大檔案傳完。工作自己的事（列出資料夾、新檔案、到期的重試）優先：協助的連線一發現就不再拿新的讀取，把在途的回答完就去做，做完沒事再回來。狀態裡每個進行中的檔案多一個 `connections`，網頁在進度下方顯示「N 條連線」。限制：所有通道的回答要依序寫入，一條連線停住時，其他連線在自己的空位填滿之後也得等它（最久到它的 30 秒用完）。量測（release 建置，測試用的 SSH 伺服器前加一段只增加延遲的轉送，往返 200 毫秒、沒有頻寬上限，一個 1 GiB 的檔案，各兩輪）：1 條連線 17.3 秒、2 條 12.6 秒、4 條 10.0–10.1 秒、8 條 8.3–8.4 秒（每條連線各自從 16 個讀取開始加深，所以不是等比例）。在開發堆疊上對真的 OpenSSH sshd（連線限速 4 MB/s，一個 512 MiB 的檔案、4 條連線）：1.1 秒後 4 條連線都在讀這個檔案，途中放進來源資料夾的 1 MiB 檔案 2.7 秒後就在本機（大檔案那時降到 3 條連線，之後回到 4 條），兩個檔案的 SHA-256 都與來源相同。頻寬被限制時多條連線不會更快；真實路徑（多跳 VPN）上的速度還沒有量。
- **先後順序**（2026-11-11，`job.rs` 的 `Sched::fits`／`takeable`）：新檔案依大小由小到大下載（同樣大小依檔名；伺服器沒有回報大小的排最後），之前是依檔名。至少 64 MiB（`Options::large_file`）的是大檔案：一個工作同時最多下載「連線數 − 1」個大檔案（只有一條連線時 1 個），剩下的那條連線下載小檔案，沒有小檔案時去協助一個大檔案——新來的小檔案不必等大檔案傳完，那條連線把在途的讀取回答完就接手。反過來，只要有另一條連線留給小檔案，沒有大檔案在下載時，下一條空出來的連線先拿大檔案：源源不絕的小檔案不會讓大檔案一直等。之前中斷、到期要接著下載的檔案仍然最優先，其中的大檔案同樣受這個上限限制（輪不到的等其他大檔案結束，不是等時間）。量測（開發堆疊對真的 OpenSSH sshd，連線限速 4 MB/s、3 條連線，同時列出 4 個 96 MiB（檔名排前面）與 6 個 1.5 MiB 的檔案）：之前第一個小檔案 77.3 秒後才在本機、最後一個 80.2 秒，3 個大檔案先傳完；現在第一個 1.4 秒、最後一個 3.8–4.2 秒（兩輪），那時還沒有大檔案傳完，同時下載的大檔案最多 2 個、一個大檔案最多 3 條連線，全部傳完的時間不變（104.1 秒 → 103.6–103.7 秒），10 個檔案的 SHA-256 都與來源相同。
- **主機金鑰**：第一次連線時記下（TOFU，`ssh_download_state`），之後只接受這把；伺服器金鑰改變時工作停止（「需要處理」）、不送出任何登入資料，網頁顯示兩個指紋，使用者確認後才信任新的（送出的指紋必須等於伺服器提供的那把）。
- **本機與秘密**：本機資料夾必須以 `/` 或 `~/` 開頭、屬於執行 VPN Manager 的使用者、群組與其他人不能寫入、不是符號連結（不存在時建立為 0755）；部分檔目錄 0700、以 `O_NOFOLLOW` 開啟。私鑰檔必須屬於使用者、權限 0600（與 OpenSSH 相同）、最大 64 KiB。密碼與金鑰密碼只在 vault（kind `ssh_download_password`、`ssh_download_key_passphrase`），工作只存參照，任何 API 都讀不回（第 9 條）；含秘密的建立與更新以 keyed fingerprint 做 idempotency。
- **上限**：最多 32 個工作；每個工作 1–8 條連線（預設 3），整個 manager 最多 24 條、在途的讀取合計最多 128 MiB；一次列出最多 10 000 個名稱；保留最近 1000 筆完成或失敗的紀錄、每個工作 500 筆日誌；檔案 I/O 在 blocking 執行緒，不卡住 runtime。暫停、刪除與 manager 停止都不等慢的伺服器（10 秒後強制結束，下次從紀錄繼續）。
- **SSH 函式庫**：`russh =0.65.1`（`aws-lc-rs` 後端，建置裡本來就有 aws-lc）＋`russh-sftp =3.0.1`，純 Rust。原工具的 libssh2 要多帶 C 函式庫與 OpenSSL、只能用它自己開的 socket、而且是 blocking；russh 直接跑在代理埠交回的 SOCKS 串流上，主機金鑰檢查是回呼（TOFU 由元件決定）。建置不含 russh 的 `rsa` feature（2026-11-11）：它帶進的 `rsa` crate 停在有 RUSTSEC-2023-0071 的預覽版，上游還沒換成修正版。所以 RSA 的使用者金鑰在讀取時就拒絕並說明原因，只有 RSA 主機金鑰的伺服器交握失敗；ed25519 與 ECDSA 照常。
- **流量（2026-11-06：經過 VPN 的 SSH，包含 SSH 下載，也顯示流量）**：工作唯一的連線是代理埠的 SOCKS5，代理埠的 splice 本來就把每個 byte 算進這個代理埠與它的連線的 payload（`GatewayRates`、連線的 payload、總覽、數據統計、頂欄），不重複計算；代理埠另把它記成「SSH 下載」（見下一條）。另外每個工作的 session 串流包一層計數（`crates/ssh-download/src/wire.rs`），`SshDownloadStatus` 帶 `wire_rx_bytes`／`wire_tx_bytes`（含 SSH 封包與加密，manager 這次啟動工作以來）、`wire_rx_bps`／`wire_tx_bps`（bytes/s，以至少 1 秒前的樣本計算）與 `running_since`；流量停了以後發布器再送一次狀態，速率不會停在舊值。網頁的清單顯示 ↓／↑ 速率，inspector「SSH 流量」顯示速率、累計、執行時間與承載它的代理埠（連結）。
- **代理埠裡的 SSH：SSH 下載與 SSH 代理分開（2026-11-07：總覽裡 SSH 下載與 SSH 代理各自顯示，不和一般代理混在一起）**：代理埠在建立 TCP 連線時決定它算哪一類（`TcpClass`，`crates/instance/src/counters.rs`），每個 byte 除了 payload 之外只加到其中一類：**SSH 下載**（`ssh_pull_rx_bytes`／`ssh_pull_tx_bytes`）是 VPN Manager 自己的 SSH 下載工作；**SSH 代理**（`ssh_rx_bytes`／`ssh_tx_bytes`，另有開著的連線數 `ssh_sessions`）是其他 SSH 連線：`vpnctl ssh-proxy`（SSH 主機的 ProxyCommand、SSH 主機的連線測試），以及沒有標記、目的 port 22 的連線；其餘是一般代理流量。用戶端以 SOCKS5 的私有 method 標明自己（`vpn_ipc::identity::GATEWAY_MARK_SSH_PULL` 0x82、`GATEWAY_MARK_SSH_SESSION` 0x81，列在 `GATEWAY_AUTH_METHOD` 之後；代理埠從不選它們，舊版代理埠會忽略，只依 port 分類），標記優先於 port：SSH 下載連到 22 埠也只算 SSH 下載，`vpnctl ssh-proxy` 連到其他 port 也算 SSH 代理。標記只影響計數，連線本身的處理完全相同；它是用戶端自己宣告的（本機程式可以假冒，只會讓統計歸錯類，不影響存取）。之前到 22 埠的 SSH 下載也算在 SSH 裡，連到其他 port 的 `vpnctl ssh-proxy` 則完全不算。worker 回報（`GatewayStatusWire`，serde default）→ `GatewayRates.ssh_rx_bps`／`ssh_tx_bps`／`ssh_sessions` 與 `ssh_pull_rx_bps`／`ssh_pull_tx_bps`（bit/s，是 payload 的一部分、不另加），並保存成數列（§6 metrics 第 8 步）。只記每個代理埠的這兩類總量，不記主機、位址或任何目的地資料。經 HTTP 代理以一般請求（非 CONNECT）送到 22 埠的不算 SSH。網頁：總覽的流量路徑每條連線另有「SSH 下載」與「SSH 代理」節點與各自顏色的線（工作數、SSH 連線數、↓／↑），代理埠節點只顯示一般代理流量；總覽的流量圖、頂欄 popover、數據統計的摘要、讀數與各連線分解表、代理埠與連線的 inspector 都把兩者分開列出（docs/frontend-design.md）。實測（dev stack，lab peer 把 tunnel 內的 2222 埠轉到本機的 sshd）：SSH 下載工作 34 Mbps 只出現在 SSH 下載、兩條 `vpnctl ssh-proxy` 連線 ↓ 6 ↑ 3 Mbps 與連線數 2 只出現在 SSH 代理；同一個代理埠上，帶 SSH 下載標記連到 22 埠的連線只算 SSH 下載，不帶標記的算 SSH 代理。
- **清除紀錄、不記錄檔名（2026-11-07：檔名可能敏感，紀錄要能清除）**：日誌與傳輸紀錄寫著遠端的檔名與路徑。**清除**：`DELETE /v1/ssh-downloads/{id}/log` 刪除工作的全部日誌、`DELETE /v1/ssh-downloads/{id}/transfers` 刪除完成與失敗的紀錄（Idempotency-Key；回答刪了幾筆 `SshDownloadCleared`，重送同一個 key 回答第一次的數字）；未完成的紀錄保留——中斷的檔案從它接著下載——也不動任何檔案（本機與遠端資料夾都不變）。清除後日誌只有一行 `LOG_CLEARED`／`HISTORY_CLEARED`（筆數，不含檔名）。網頁在工作的「紀錄」「日誌」分頁與 ⋯ 選單（破壞性那一組）各有「清除傳輸紀錄…」「清除日誌…」，先以確認說明範圍；`vpnctl ssh-download clear-log|clear-history <工作> --yes`。**刪除不留痕跡**：control 資料庫的寫入連線開 `secure_delete`（刪除的內容以 0 覆寫：資料庫的空閒頁與頁內空間都不留）；清除、依天數刪除、刪除工作，以及不記錄檔名的工作每完成一個檔案之後，WAL 都 checkpoint 並截斷為 0（`wal_checkpoint(TRUNCATE)`，有讀取者擋住時重試；WAL 裡沒有刪除前的頁面影像）；每小時再截斷一次，涵蓋只保留最新 500 行／1,000 筆的逐筆淘汰。開 `secure_delete` 之前留在空閒頁的舊內容，在這版第一次啟動時 `VACUUM` 一次去掉（`meta.secure_delete_since`；空間不夠時下次啟動再做）。檔案系統自己可能留下檔案以前的內容（journal、copy-on-write、快閃記憶體的磨損平均），那只有全磁碟加密能處理。**不記錄檔名**（工作的 `record_names`，預設開）：關掉後，完成的檔案在紀錄裡只留傳輸編號（`#3f2a9c1d`，紀錄 id 的開頭；`source_path` 空白、沒有本機路徑，失敗的只記失敗資料夾），日誌的 `file` 也是編號，訊息不寫路徑，伺服器與本機的原因裡出現的檔名與路徑換成編號（`crates/ssh-download/src/record.rs`）；未完成的檔案在完成前保留檔名與路徑（接續與放置需要），下載中的檔名仍即時顯示在狀態（不保存）。**保留天數**（`history_days`，1–3650，預設不限）：超過的日誌與完成的紀錄每小時刪除（也在儲存設定時刪一次），之後截斷 WAL。**日誌檔**：manager、controller 與 worker 的日誌不寫檔名或路徑（SSH 下載的 tracing 只有工作 id、紀錄 id 與錯誤種類；dev stack 實測下載與清除後 `mgr.log`、`ctl.log`、`lab.log` 都找不到檔名）。**備份**：installer 升級時的資料庫備份（§5.5）在複製後清掉所有工作的日誌與完成的紀錄、`VACUUM` 並截斷 WAL（`crates/installer/src/scrub.rs`；未完成的紀錄保留，回復後接著下載；清不掉時保留原備份並說明）。診斷報告與事件記錄本來就不含 SSH 下載的檔名。
- **沒有做**：以 `vpnctl` 建立或編輯工作（只有 `list`、`clear-log`、`clear-history`、`records --names on|off --keep-days N|off`）；匯入原工具的 `.records`。

## 7d. 介面語言

2026-11-11 新增：網頁與服務寫給人看的文字有繁體中文、英文、日文；CLI（`vpnctl`、`vpn-installer`）維持繁體中文。

- **服務端**：寫給人看的文字是 `vpn_domain::Text`（`crates/domain/src/text.rs`），以 `tr!(英文, 繁體中文, 日文; 名稱 = 值)` 寫成；只有一個指標寬（文字在 `Box` 後面，帶著它的錯誤與紀錄不變大）。JSON 是 `{"en", "zh-TW", "ja"}` 物件；讀到之前留下的一段字串時，三種語言都是那段字（Store 的欄位經 `crates/store/src/text_column.rs`，舊資料照讀）。名稱、供應商與遠端的原話這類不分語言的文字用 `Text::verbatim`。服務不知道讀者的語言，三種一起送；只有不是 JSON 的回答——代理埠與 App 本機存取埠拒絕 HTTP 請求時的純文字——依請求的 `Accept-Language` 選一種（任何中文算繁體中文），沒有可用的語言時英文。
- **網頁**：`web/src/i18n/`（規則與用語見其 `README.md`）。語言在載入時決定一次：這個瀏覽器記住的選擇 → 瀏覽器的語言 → 英文；頂欄的語言選單記住新的選擇並重新載入頁面，所以模組層的訊息表與 `Intl` 格式器不會過期。每段文字在功能旁的 `messages.ts(x)`，英文表是基準，另兩表由 TypeScript 檢查同形；服務的 `Text` 以 `localized()` 取這頁的語言。
- **檢查**：ESLint 拒絕訊息表以外的 CJK 字面值；`scripts/text_guard.py`（`scripts/check.sh` 執行）拒絕 Rust 產品程式碼中 `tr!` 以外的 CJK 字串，以及英文參數含 CJK 的 `tr!`（測試、`vpnctl`、`installer` 不檢查）。
- **相容性**：2026-11-11 之前這些欄位是一段繁體中文字串。直接讀 API 的工具要讀物件裡的語言，或只看代碼（`code`、`reason_code`、列舉）——用中文字比對的程式會悄悄不成立。`vpnctl --json` 的錯誤 `message` 一律是三語物件（vpnctl 自己的訊息三種語言都是繁體中文）。
- **使用者可以改的名稱**：IP 封鎖清單的名稱是一段字串，內建清單以目錄的繁體中文名稱建立；名稱沒改過時網頁顯示目錄裡這頁語言的名稱，存檔時保留原本存的名稱。網頁建立 Provider 連線時一併建立的代理埠，以讀者的語言命名（`ProviderConnectInput.gateway_name`，沒有時 `Gateway <port>`）。

## 8. 必須持續成立的不變量

1. 受保護 payload 沒有 direct fallback（結構保證：worker 無任意目的 host socket；Linux strict 模式 netns 內無其他介面；本機存取埠的 relay 只接收主機交來的連線、不往外連，第 12 條）。
2. controller／Store／metrics 不轉送 payload。
3. gate 只能由 manager 的 Activate 開啟；內層只能收緊；`sealed` 永不重開。
4. DNS 一律經 tunnel；無 host resolver fallback；TLS 驗證失敗不降級（同一個伺服器不會改用明文）。DNS 設定的伺服器全部失敗時改用的是 WireGuard 設定宣告的 DNS，同樣經 tunnel，而且狀態會說（§4.1）；DNS 設定選了失敗時中斷（`on_failure: fail`）時連它都不問：一個查詢都不送給它，查詢在期限內立刻失敗（`crates/instance/tests/dns.rs`）。
5. IPv6：profile 有 IPv6 位址就經 tunnel，否則明確拒絕，不讓 OS 找替代路由。
6. 同一 WireGuard 金鑰同時只有一個存活 worker。
7. 使用者的 Stop／急停意圖不會被自動恢復覆蓋。
8. 所有佇列、buffer、parser、查詢有上限。
9. 秘密不進 log、argv、env、一般 API、SSE、metrics。
10. 管理介面預設只在 loopback；驗 Host／Origin／Fetch-Metadata；無 CORS；沒有登入。誰能連，在 accept 時、讀取任何資料前就決定（每條連線一次，keep-alive 與 SSE 沿用；`crates/platform/src/admission.rs`、`crates/controller/src/tcp_listener.rs`）：這台主機上的 client（loopback 或主機自己的位址）只服務執行 VPN Manager 的同一個使用者的程式——`api.sock` 以 peer credentials 確認；TCP 查出連線另一端 socket 的擁有者（Linux 讀 `/proc/net/tcp{,6}` 的 uid 欄，macOS 以 libproc 走訪本使用者的程序找出持有該 socket 的程序；`crates/platform/src/peer.rs`），不是同一個 UID、找不到或查詢失敗都直接關閉並記錄（fail closed；`ssh -L` 轉發算本使用者的：持有 socket 的是本使用者的 sshd session 程序）。只有以 `--listen-address`（非 loopback）＋`--allow-client` 安裝時才服務其他主機，而且來源必須在列出的網段（從主機自己的區網位址連入時兩個條件都要符合）；這時 Host／Origin 另外接受「主機自己的非 loopback、非 link-local 位址＋管理 port」，只認數字位址、不認主機名稱（防 DNS rebinding）。允許網段裡的任何裝置都能完整操作 VPN Manager（§9）。
11. worker 對 host 網路只有兩種連線，都在 loopback：代理埠的 SOCKS5 UDP relay（綁在 client 的 loopback 位址，只回給該 client），以及轉發連到受管 App 的 `AppEndpoint`——只接受 loopback 位址與 ≥1024 的 port，只連 manager 的 lease 所指、且核對過由 App 程序樹持有的那個位址；lease 撤銷就 reset。轉發從不在 host 介面監聽（只在 tunnel 位址）。`crates/instance/tests/host_sockets.rs` 掃描原始碼確保沒有其他建立 host socket 的地方。
12. 本機存取埠（§4.3）只把連線送進 sandbox、不開往外的路：manager 持有主機上的 listener，每條連線經第 10 條同一個判斷（這台主機＝同一個使用者的程式；其他主機＝只有 `lan` 的 port、只在它的允許網段）；sandbox 內的 relay 只接 manager 以 SCM_RIGHTS 交來的連線、只連 App 這次執行設定的 App port（sandbox 的 loopback），從不監聽、不連其他位址，沒有 capability，同時最多 256 條，隨 App 的 launcher 結束。這條路徑不經 tunnel 與目的地政策；App 自己的流量仍只經 tunnel（第 1 條）。
13. 轉發的 PROXY protocol 標頭（§4.1）只寫 tunnel 上看到的事實，App 只能在這個轉發送它的 port 上相信它：其他連得到同一個 port 的程式也能自己送一個標頭——非 strict 的 App 是這台主機上的本機程式，strict App 是 sandbox 裡的程式，以及開到同一個 App port 的本機存取埠（第 12 條）。worker 的標頭永遠在遠端的第一個位元組之前，遠端自己送的標頭只會是 payload；但轉發關閉這個設定時 App 也必須關閉，否則遠端可以在開頭自己送一個假的來源。標頭只走既有的 `AppEndpoint` 連線，不改變第 11 條：worker 仍只連 lease 指定的 loopback 位址。
14. SSH 下載只經代理埠（§7c）：元件唯一的連線是 loopback 上自己代理埠的 SOCKS5（附安裝金鑰證明、伺服器名稱不在主機解析）；沒有路由、代理埠拒絕或連線未就緒時等待，從不直連（`crates/ssh-download/tests/no_direct.rs` 掃描原始碼；`tests/engine.rs` 證明代理埠不能承載時伺服器收不到任何連線）。
15. UDP 直接送進沙箱（§4.1）不開新的路：datagram 只走 tunnel → 封包過濾 → TUN → sandbox 裡 App 自己的 socket，worker 沒有為它開任何 socket（第 11 條不變）、不連 App、也不轉換位址。過濾只讓「轉發的 lease 有效、gate 開啟、經轉發的 `InboundGuard` 與上限 admit」的新遠端進來，只到登記的那一個 tunnel port；其他 port、其他時候、被拒的來源一律丟棄。admit 的遠端在 sandbox 裡看到的仍是 tunnel 位址上的那一個 port：連得到的只有持有它的 App；manager 確認持有者是這個轉發的嚴格隔離 App、沒有其他程式在同一個 port 的可達位址上（每 2–5 秒核對，與其他轉發相同的限制：兩次核對之間換手看不到）。App 在這些 flow 上的回覆只回到那個遠端，App 要連其他地方仍經目的地政策（第 1 條）。
16. SSH 下載清除或過期的紀錄不留在資料庫（§7c）：清除、依天數刪除與刪除工作之後，刪掉的檔名不在 control 資料庫的檔案與 WAL 裡，同一個工作未完成的紀錄與其他工作的紀錄都還在，未完成的檔案照常接續（`crates/ssh-download/tests/engine.rs` 讀資料庫檔案檢查）；升級備份不帶日誌與完成的紀錄（`crates/installer/src/scrub.rs`）。
17. 多跳只走確認過的 port（§7）：Mullvad 多跳的 endpoint 是入口 relay 的 IPv4 加上 Mullvad 網站清單對到出口公鑰與 IPv4、沒有其他 relay 共用的 `multihop_port`，peer 是出口的公鑰；對不上就拒絕，不改用其他 port 或其他 relay（`crates/controller/src/provider/route.rs` 的測試）。AirVPN 的入口只用帳號 manifest 列出、狀態清單確認過位址的組合。

## 9. 取捨：一開始的構想與實際的做法

這個專案動工前有一份構想，列出要有哪些程序、協定與功能。下表是實作之後和它不同的地方：左欄是原本的構想，中間是現在的做法，右欄是理由。

| 一開始的構想 | 實際的做法 | 理由 |
|---|---|---|
| 6 種程序：controllerd、instance-managerd、platformd、stored、instance、provider-worker | 3 種：controller、manager（含 Store＋Platform）、instance | macOS explicit proxy 與 Linux rootless netns 都不需要特權，獨立 platformd 沒有工作；Store 與 Instance Manager 同程序消除「Manager 活著但 Store 程序掛掉無法恢復」的故障模式與一跳秘密 IPC；仍保留 crate 邊界（只有 `store` 用 SQLite、只有 `platform` 做 OS 呼叫）。需要特權的功能（例如未來的 NetworkExtension）再以獨立 helper 擴充 |
| Provider worker 獨立程序 | Provider 工作在 controller 內執行，憑證以租約取得、用完 zeroize；所有流量經 Instance connector 或 manager 交付的 bootstrap socket，controller 自己不能 dial | controller 本來就在 ingress 看到秘密；多一個程序只增加 FD 轉交與生命週期複雜度，防禦增益有限；真正要防的「consumed 後誤用直連」由 manager 持有並撤銷 socket 解決 |

| 網址清單下載 | 只經 Provider 出口連線（ViaInstance），不用首次直連；不做 Provider 的 IP preflight；沒有出口時清單顯示等待原因，排程不嘗試也不記為失敗，手動更新回 `PROVIDER_EGRESS_BLOCKED` 且不標為過期 | 首次直連只給供應商帳號使用；IP preflight 檢查的是供應商帳號的出口身分，與下載公開清單無關 |

| 自動封鎖的視窗 ≤300 秒、封鎖時間 ≥10 秒 | 沿用既有的驗證範圍：視窗 1–3600 秒、封鎖 1–604800 秒 | 既有的安全設定已以這些範圍儲存；收緊會讓已存的設定變成無效 |
